# 1과목 · 데이터 모델링의 이해

<br>

### 1.1 모델링의 목적과 세 가지 관점

모델링은 왜 하는가? DB를 만들려고만 하는 게 아니다. **데이터 모델링 자체가 업무를 설명하고 분석하고 소통하는 수단**이다. 이 문장이 그대로 선지로 나온다.

| 관점 | 초점 | 대표 도구 |
|---|---|---|
| 데이터 관점(Data View) | 어떤 데이터가 필요한가 (What) | ERD |
| 프로세스 관점(Process View) | 업무 절차가 어떻게 흘러가는가 (How) | 프로세스 흐름도 |
| 상관 관점(Interaction View) | 업무가 발생할 때 어떤 데이터가 C/R/U/D 되는가 | CRUD 매트릭스 |

<br>

### 1.2 데이터 독립성과 유연성

- **비유연성 해소**: 데이터의 사용 프로세스와 데이터의 정의를 분리한다. 그래야 데이터나 프로세스가 조금 바뀌어도 애플리케이션과 DB 전체가 흔들리지 않는다.
- 특정 업무 프로세스나 화면에 데이터 구조를 종속시켜 설계하면 **업무 변경에 극도로 취약**해진다.
- 좋은 모델링의 목표는 데이터와 프로세스를 분리해 유지보수성과 확장성을 확보하는 것이다.

<br>

### 1.3 엔터티 — 발생 시점에 따른 분류

암기 키워드는 **기·중·행**이다.

| 구분 | 성격 | 예시 |
|---|---|---|
| 기본/키 엔터티 | 업무에 원래 존재하는 고유 엔터티. 다른 엔터티의 부모 역할 | 사원, 부서, 고객, 회원, 상품 |
| 중심(메인) 엔터티 | 기본 엔터티로부터 발생하며 업무의 중심 역할. 행위 엔터티를 생성 | 주문, 청구, 매출, 구매 |
| 행위 엔터티 | 2개 이상의 엔터티로부터 계속 발생하는 트랜잭션성 엔터티 | 주문상세, 이력, 구매이력 |

<br>

### 1.4 속성 — 파생 속성

데이터 조회 성능을 높이려고 원래 속성값을 가공·계산해서 별도로 저장해 둔 속성이다. 총금액, 결제건수 같은 것들이 여기 해당한다.

<br>

### 1.5 관계와 표기법

**관계 표기법의 3요소**: 관계명, 관계차수(Cardinality), 선택성(선택사양)

**피터 첸(Peter Chen) 표기법 도형**

| 도형 | 의미 |
|---|---|
| □ 직사각형 | 엔터티(Entity) |
| ◇ 마름모 | 관계(Relationship) |
| ○ 타원 | 속성(Attribute). 기본키 속성은 타원 안에 밑줄 |
| — 선 | 엔터티–속성, 엔터티–관계 연결. 선 위에 1:1, 1:N, N:M 표기 |

**Barker 표기법**은 exclusive 표시를 통해 상호배타적 관계(배타 관계)를 표현할 수 있다.

<br>

**본질 식별자 vs 인조 식별자**

- 사번은 업무적으로 의미를 가지는 **본질 식별자**다. 인조 식별자가 아니다.
- 본질 식별자는 반드시 **업무적인 규칙과 행위 안에서** 발생한다.
- 그래서 본질 식별자는 **업무 규칙이 바뀌면 값이 변경될 수 있다.** 정책이나 업무 프로세스가 바뀌는 순간이 그렇다.
- 인조 식별자를 남용하면 본질 식별자에 대한 별도의 `UNIQUE` 인덱스를 추가로 만들어야 해서 **인덱스 오버헤드**가 생긴다.

**식별자 상속**

A → B → C로 식별관계가 연쇄되면 부모의 PK가 자식의 PK 구성원으로 상속된다. 즉, 최종 하위 엔터티는 상위 엔터티들의 PK를 **누적해서** 상속받는다.

<br>

### 1.7 UNIQUE 제약조건

후보키 중 기본키로 뽑히지 못한 나머지, 즉 대체키를 물리적으로 구현하는 수단이 `UNIQUE`다.

| 구분 | PRIMARY KEY | UNIQUE |
|---|---|---|
| 개념적 매핑 | 기본키(PK) | 대체키(AK) / 보조 식별자 |
| 중복 허용 | 불가 | 불가 |
| NULL 입력 | **불가** (NOT NULL 필수) | **허용** |
| 테이블당 개수 | 오직 1개 | 여러 개 |
| 인덱스 | Unique Index 자동 생성 | Unique Index 자동 생성 |

**NULL 처리는 DBMS마다 다르다**

- **Oracle**: NULL을 "알 수 없는 값"으로 본다. 서로 같은지 판단할 수 없으니 `UNIQUE` 컬럼에 NULL이 여러 개 들어가도 에러가 나지 않는다.
- **SQL Server**: NULL도 하나의 고유한 값으로 취급해서 **NULL은 1개만 허용**한다. 두 번째부터 중복 에러다. (Filtered Index로 다중 NULL 허용은 가능)

> `UNIQUE`는 `NOT NULL`을 별도로 붙이지 않는 한 NULL 저장을 허용한다.

<br>

### 1.8 정규화

- 정규화는 **논리 데이터 모델링 상세화 과정**의 대표 활동이다. 개념 모델링이 아니다.
- **제1정규형**: 원자성 확보
- **제2정규형**: 부분 함수 종속성 제거 → 주식별자 전체에 완전 종속
- **제3정규형**: 이행적 함수 종속성 제거 → 일반 속성 간 종속 제거

여기서 자주 나오는 선지 두 개.

- "제3정규형을 만족하는 엔터티의 일반 속성은 주식별자 전체에 종속적이다" → **참(O)**
- 3정규화는 **주식별자 선정과 가장 관련이 적다.**

<br>

### 1.9 함수 종속성과 후보키

속성 [A, B, C, D, E], 결정자 관계가 `AB→CDE`, `E→B`, `D→AB`일 때.

| 후보 | 판정 | 근거 |
|---|---|---|
| AB | 가능 | AB→CDE로 전체 결정 |
| AE | 가능 | E→B이므로 AE로 AB를 유도 → CDE까지 결정 |
| D | 가능 | D→AB→CDE |
| AC | **불가** | 모든 속성을 결정할 수 없음 |

<br>

### 1.10 참조무결성 — 부모·자식 관계 규칙

**삭제 규칙(Delete Rule)**

| 옵션 | 동작 |
|---|---|
| `RESTRICT` | 자식 데이터가 있으면 부모 삭제 불가 (가장 보수적) |
| `CASCADE` | 부모 삭제 시 자식도 연쇄 삭제 |
| `SET NULL` | 부모 삭제 시 자식의 외래키 값을 NULL로 변경 |

**입력 규칙(Insert Rule)**

| 옵션 | 동작 |
|---|---|
| `Dependent` | 부모에 해당 PK가 이미 있을 때만 자식 입력 허용 |
| `Automatic` | 부모에 PK가 없으면 부모를 자동 생성한 뒤 자식 입력 허용 |

# 2과목 · SQL 기본 및 활용

### 2.1 SQL 기본 구조

- `SELECT`, `FROM` 절은 필수 구문이다.
- 테이블 생성·수정·삭제처럼 구조를 정의하는 언어는 **DDL**이다.
- 특정 조건의 행만 걸러내는 절은 `WHERE`다.
- `SELECT DISTINCT col1, col2`는 **나열된 모든 컬럼의 조합**이 완전히 같은 행만 중복 제거한다. col1만 보고 지우는 게 아니다.

<br>

### 2.2 NULL — 정체는 FALSE가 아니라 UNKNOWN

가장 많이 틀리는 지점이라 먼저 못을 박아두자. **NULL에 대한 모든 비교 연산 결과는 FALSE가 아니라 UNKNOWN이다.** (`IS NULL` / `IS NOT NULL` 제외)

```sql
SELECT * FROM dual WHERE NULL = NULL;        -- 0 rows
SELECT * FROM dual WHERE NOT (NULL = NULL);  -- 이것도 0 rows
```

`NULL = NULL`이 정말 FALSE였다면 `NOT FALSE`는 TRUE가 되어 두 번째 쿼리는 행을 반환해야 한다. 그런데 실제로는 둘 다 0건이다. 즉, FALSE가 아니라는 증거다.

```sql
CREATE TABLE t (price NUMBER CHECK (price > 0));
INSERT INTO t VALUES (NULL);  -- 성공
```

`CHECK` 제약조건은 **FALSE일 때만 위반**으로 판단하고 UNKNOWN은 통과시킨다. 정말 FALSE였다면 이 INSERT는 실패했을 것이다.

**WHERE 절의 최종 필터링 기준**

1. 컬럼이 NULL이면 `COL1 = 10`은 `NULL = 10` → UNKNOWN
2. `TRUE AND UNKNOWN` → UNKNOWN / `FALSE AND UNKNOWN` → FALSE
3. `WHERE` 절은 **오직 TRUE인 행만 통과**시킨다. FALSE도 UNKNOWN도 전부 탈락이다.

이 규칙 때문에 INNER JOIN과 NATURAL JOIN에서도 **조인 컬럼에 NULL을 포함한 행은 생략된다.**

**NULL 연산과 집계**

- `NULL + 숫자 = NULL` → `SUM(NULL) + SUM(20) = NULL`
- Oracle은 빈 문자열 `''`를 NULL로 취급한다 (`IS NULL`로 조회).
- SQL Server는 `''`를 **길이 0인 문자열**로 취급한다 (`IS NULL` 불가).
- `'001'`과 `'1'`은 문자열 비교 시 서로 다르다.

**공집합 vs NULL 반환**

| 대상 | 조건 만족 행이 없을 때 |
|---|---|
| `COUNT(*)` | **0** 반환 |
| `SUM`, `AVG`, `MAX`, `MIN` | **NULL** 반환 |
| 일반 컬럼 조회 (`SELECT col`) | **공집합(0행)** |

**NOT IN + NULL = 공집합**

서브쿼리 결과가 `(7902, 7698, NULL, 7566, NULL)`일 때 다음 쿼리는 몇 건이 나올까?

```sql
SELECT *
FROM EMP
WHERE EMPNO NOT IN (SELECT MGR FROM EMP);
```

답은 **공집합(0건)**이다. `NOT IN`은 내부적으로 AND 조건의 연속으로 풀린다.

```
EMPNO != 7902 AND EMPNO != 7698 AND EMPNO != NULL AND ...
```

`EMPNO != NULL`이 UNKNOWN이 되는 순간 AND 전체는 절대 TRUE가 될 수 없다. `IN`은 OR로 풀리기 때문에 결과가 다르다.

### 2.3 단일행 함수 — 문자·날짜 변환

- `TO_CHAR(날짜, 'YYYYMM')` — 날짜를 6자리 연월 문자열로 자른다. 1월 1일이든 1월 31일이든 전부 `'201501'`로 뽑힌다.
- `TO_DATE('201501', 'YYYYMM')` — 연월 문자열을 **일자가 1일인 정각 시점**(`2015-01-01 00:00:00`)으로 변환한다. 뭉뚱그린 문자열이 아니라 특정 시점이 나온다는 게 차이다.
- `SYSDATE + n/24` — n시간 후
- `TRUNC(SYSDATE)` — 당일 `00:00:00`으로 시간 절삭
- `SUBSTR(문자열, m, n)` — m번째부터 n개 추출

**연·월·일 추출은 DBMS별로 문법이 다르다**

| 구분 | Oracle `EXTRACT` | SQL Server `DATEPART` |
|---|---|---|
| 문법 | `EXTRACT(YEAR FROM 날짜)` | `DATEPART(YEAR, 날짜)` |
| 구분자 | `FROM` 키워드 필수 | 쉼표(`,`) |
| 반환 타입 | NUMBER | INT |
| 비고 | `FROM DUAL` 필요 | `FROM DUAL` 불필요 |

```sql
-- Oracle
SELECT EXTRACT(YEAR FROM SYSDATE) AS 연도,
       EXTRACT(MONTH FROM SYSDATE) AS 월,
       EXTRACT(DAY FROM SYSDATE) AS 일
FROM DUAL;

-- SQL Server
SELECT DATEPART(YEAR, GETDATE()) AS 연도,
       DATEPART(MONTH, GETDATE()) AS 월,
       DATEPART(DAY, GETDATE()) AS 일;
```

**문자열 리터럴 속 작은따옴표**

SQL 문자열 리터럴에서 연속된 작은따옴표 2개(`''`)는 문자로서의 작은따옴표 1개(`'`)를 의미한다.

```sql
SELECT '''A''''' R1 FROM DUAL;
```

작은따옴표 8개를 앞에서부터 분해하면 이렇게 된다.

| 위치 | 해석 |
|---|---|
| 맨 앞 `'` | 리터럴 시작 |
| `''` | 문자 `'` 1개 |
| `A` | 문자 `A` |
| `''` | 문자 `'` 1개 |
| `''` | 문자 `'` 1개 |
| 맨 뒤 `'` | 리터럴 끝 |

최종 결과는 `'A''`다.

### 2.4 정규표현식

**메타 문자**

| 표현식 | 설명 | 표현식 | 설명 |
|---|---|---|---|
| `\d` | 숫자 | `\n` | 엔터(줄바꿈) |
| `\D` | 숫자가 아닌 모든 것 | `[[:digit:]]` | 숫자 |
| `\w` | 글자(영어·숫자·한글) + `_` | `[[:alpha:]]` | 문자 |
| `\W` | 글자가 아닌 모든 것(특수기호·공백) | `[[:alnum:]]` | 숫자 + 문자 |
| `\s` | 공백 | `[[:punct:]]` | 특수기호(`_` 포함) |
| `\t` | 탭 | | |

**문자 클래스**

| 패턴 | 설명 | 패턴 | 설명 |
|---|---|---|---|
| `[ab]` | a 또는 b 한 글자 | `[A-z]` | 영문 한 글자 (대소구분 X) |
| `[a-z]` | 영문 소문자 한 글자 | `[가-힣]` | 한글 한 글자 |
| `[A-Z]` | 영문 대문자 한 글자 | `[^ab]` | a와 b를 제외한 문자 |

**위치·그룹**

| 표현식 | 설명 | 표현식 | 설명 |
|---|---|---|---|
| `.` | 엔터를 제외한 모든 한 글자 | `a\|b` | a 또는 b |
| `^` | 시작 | `()` | 그룹 지정 |
| `$` | 끝 | `\` | escape character |

**match_parameter 옵션**

| 옵션 | 설명 |
|---|---|
| `c` | 대소문자 구분 (Case-sensitive) |
| `i` | 대소문자 구분 안 함 (Case-insensitive) |
| `m` | 패턴을 다중라인으로 선언 (Multi-line) |

**REGEXP_SUBSTR의 subexpr**

```
REGEXP_SUBSTR(source_string, pattern, position, occurrence, match_parameter, subexpr)
```

```sql
SELECT REGEXP_SUBSTR('123-234-4545-233', '((\d+)-(\d+))-((\d+)-(\d+))', 1, 1, NULL, 4)
FROM DUAL;
```

| 인자 | 값 | 의미 |
|---|---|---|
| source_string | `'123-234-4545-233'` | 대상 문자열 |
| pattern | `'((\d+)-(\d+))-((\d+)-(\d+))'` | 정규식 |
| position | `1` | 1번째 문자부터 검색 시작 |
| occurrence | `1` | 첫 번째로 매칭되는 것 |
| match_parameter | `NULL` | 기본 옵션 |
| **subexpr** | **`4`** | 4번째 괄호(서브그룹)만 반환 |

핵심은 괄호 번호를 **여는 괄호가 나온 순서대로** 매긴다는 점이다. 겉으로 보이는 큰 그룹이 먼저 번호를 받고(①④), 그 안의 작은 그룹이 다음 번호를 받는다(②③, ⑤⑥).

```
( ( \d+ ) - ( \d+ ) ) - ( ( \d+ ) - ( \d+ ) )
①  ②        ③          ④  ⑤        ⑥
```

| 그룹 | 패턴 | `'123-234-4545-233'` 대입 결과 |
|---|---|---|
| ① | `(\d+)-(\d+)` | `123-234` |
| ② | `\d+` | `123` |
| ③ | `\d+` | `234` |
| **④** | `(\d+)-(\d+)` | **`4545-233`** |
| ⑤ | `\d+` | `4545` |
| ⑥ | `\d+` | `233` |

`subexpr = 4`이므로 정답은 **`4545-233`**이다.

**REGEXP_LIKE**

- 대상 문자열이 지정한 정규식 패턴과 일치하는지 검사하는 **조건식**이다.
- 문법: `REGEXP_LIKE(source_string, pattern, [match_parameter])`
- 값을 반환하는 함수가 아니라 참/거짓을 판단하므로 `WHERE`나 `HAVING` 절의 조건식으로 주로 쓴다. 조건(condition)이 올 수 있는 자리라면 어디서든 사용 가능하다.

### 2.6 GROUP BY와 HAVING

- `GROUP BY`를 쓴 쿼리의 `SELECT`, `HAVING`, `ORDER BY` 절에는 **GROUP BY에 참여한 컬럼**이나 **집계 함수**만 올 수 있다.
- `GROUP BY` 절에는 `SELECT` 절의 **컬럼 Alias를 쓸 수 없다.**
- `GROUP BY` 없이 `HAVING`만 단독으로 쓰는 것은 문법상 가능하다. 전체를 1개 그룹으로 간주한다.

### 2.7 JOIN

- 옵티마이저는 아무리 많은 테이블을 조인해도 내부적으로 **항상 2개씩 순차 조인**한다.
- 두 테이블 간 매핑 조건이 누락되면 **카티시안 곱(Cartesian Product)**이 발생한다.
- `CROSS JOIN`은 `ON` 절을 사용할 수 없다.
- INNER JOIN과 NATURAL JOIN에서 조인 컬럼에 NULL을 포함한 행은 생략된다.

**NATURAL JOIN / USING 접두사 규칙**

`NATURAL JOIN`이나 `USING(컬럼명)`으로 조인할 때, **조인에 사용된 공통 컬럼**은 SELECT·WHERE·ORDER BY 어디에서도 테이블명이나 별칭을 붙이면 안 된다. 물론 조인에 쓰이지 않은 컬럼은 접두사를 붙여도 괜찮다. 오직 `USING` 절에 명시된 컬럼만 금지다.

```sql
-- USING(department_id)인 경우
SELECT e.employee_id,        -- OK (department_id가 아님)
       department_id,        -- OK (접두사 없음)
       d.department_name     -- OK
FROM employees e JOIN departments d USING (department_id)
WHERE department_id = 90;    -- OK
-- WHERE e.department_id = 90;  -- ERROR (WHERE에서도 접두사 불가)
```

| 구분 | 조인 컬럼 취급 | 접두사 |
|---|---|---|
| `ON` | 양쪽 테이블에 각각 별개로 존재 | 반드시 필요 (모호성 해소) |
| `USING(컬럼)` | 지정한 컬럼만 하나로 병합 | 해당 컬럼만 금지, 나머지는 자유 |
| `NATURAL JOIN` | 이름이 같은 모든 컬럼이 자동 병합 | 그 컬럼들 전부 금지 |

**OUTER JOIN — ON과 WHERE는 적용 시점이 다르다**

OUTER JOIN의 목적은 기준 테이블(보존되는 쪽)의 행을 매칭 여부와 상관없이 결과에 남기는 것이다. 그런데 조건을 어디에 넣느냐에 따라 이 "무조건 보존"이 깨진다.

### 2.8 관계대수 순수 관계 연산자 4종

| 연산자 | 기호 | 연산 방향 | SQL 매핑 | 핵심 개념 |
|---|---|---|---|---|
| SELECT | σ (시그마) | 가로 (행, 튜플) | `WHERE` | 조건에 맞는 행만 수평 분할 |
| PROJECT | π (파이) | 세로 (열, 속성) | `SELECT 컬럼` | 원하는 컬럼만 수직 분할 |
| JOIN | ⋈ | 테이블 결합 | `JOIN ... ON` | 공통 속성 기준으로 합침 |
| DIVIDE | ÷ (또는 %) | 나눗셈 / 완전 포함 | `NOT EXISTS` 등 | B의 모든 값을 가진 행 추출 |

- 암기 팁: **S**igma → **S**ELECT(수평), **P**i → **P**ROJECT(수직), ⋈는 리본처럼 두 테이블이 묶이는 모양
- DIVIDE는 단독 명령어가 없다. `NOT EXISTS`나 `COUNT` 집계로 구현한다.

```
수학의 나눗셈:   (A × B) ÷ B = A
관계대수 DIVIDE: R(학생, 과목) ÷ S(과목) = T(학생)
```

### 2.9 집합 연산자

조인과 집합 연산자는 결합 방향부터 다르다.

| 구분 | 결합 방향 | 설명 |
|---|---|---|
| 조인(JOIN) | 가로(수평) | 관련 있는 컬럼 기준으로 옆으로 열을 확장 |
| 집합 연산자 | 세로(수직) | 개별 SELECT 결과를 위아래로 행을 쌓음 |

- `INTERSECT` → 교집합 (A∩B)
- `NOT EXISTS` → 전체(A)에서 공통(A∩B)을 뺀 차집합 (A−B)

**ORDER BY 규칙**

- 개별 `SELECT` 문 내부에는 `ORDER BY`를 쓸 수 없다.
- **전체 쿼리의 맨 마지막 줄에 오직 1번만** 작성 가능하다.
- 정렬은 집합 연산이 모두 끝난 **최종 결합 결과 전체**에 적용된다.

```sql
SELECT EMP_ID, EMP_NAME FROM EMPLOYEE_KOREA
UNION
SELECT EMP_ID, EMP_NAME FROM EMPLOYEE_USA
ORDER BY EMP_ID;   -- 맨 끝에 한 번만
```

**실행 우선순위**

```
INTERSECT  >  UNION / UNION ALL / MINUS(EXCEPT)
```

- `INTERSECT`가 가장 먼저 실행된다.
- 동일 순위 연산자는 작성된 위에서 아래 순서대로 실행된다.
- 순서를 바꾸고 싶으면 괄호 `()`로 묶는 것이 좋다.

| 절 | 역할 |

### 2.11 서브쿼리와 뷰

- **스칼라 서브쿼리는 결과가 0건이면 에러가 아니라 NULL을 반환한다.** 2건 이상일 때만 에러다.
- 스칼라 서브쿼리는 결과 건수만큼 반복 실행된다.
- 다중 컬럼 서브쿼리는 SQL Server에서 지원하지 않는다.
- **다중 행 서브쿼리**는 단일행 비교 연산자(`=`, `>`, `<`)와 단독으로 쓸 수 없다. `IN`, `ANY`, `ALL`, `EXISTS` 같은 다중 행 연산자를 써야 한다.
- 서브쿼리 내부에서는 일반적으로 `ORDER BY`를 쓸 수 없다. 단, 인라인 뷰는 예외다.
- **뷰(View)**는 SQL 쿼리 정의만 저장하고 있는 가상 테이블이다. 그래서 테이블 구조가 바뀌어도 이를 사용하는 프로그램의 수정을 최소화할 수 있다. 이걸 조금 유식한 말로 **데이터 독립성 확보**라고 한다.

<br>

### 2.12 윈도우 함수

일반 `GROUP BY`와의 가장 큰 차이는 이것이다. 윈도우 함수는 결과에 대한 함수 처리일 뿐이라 **결과 행 수를 줄이지 않는다.**

| 구분 | PARTITION BY | GROUP BY |
|---|---|---|
| 위치 | 윈도우 함수 내부(`OVER` 절) | `GROUP BY` 절 |
| 분할 방식 | 논리적 그룹핑 (기존 행 유지) | 물리적 그룹핑 (집계 후 행 합침) |
| 결과 행 수 | **변하지 않음** | **줄어듦** (그룹당 1행) |

**윈도우 프레임 — 생략했을 때 무엇이 기본값인가**

| 작성 형태 | 실제 동작 | 결과 |
|---|---|---|
| `SUM(AMT) OVER (ORDER BY SALE_DATE)` | `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` | 첫 행부터 누적 합계 |
| `SUM(AMT) OVER (ORDER BY SALE_DATE ROWS CURRENT ROW)` | `ROWS BETWEEN CURRENT ROW AND CURRENT ROW` | 현재 행 1개 → 원래 AMT 값 그대로 |

`BETWEEN ~ AND ~`를 다 쓰지 않고 단일 지점만 적으면 시작과 끝이 모두 그 위치로 설정된다는 게 두 번째 케이스의 원리다.

> **한 줄 요약**
> `ORDER BY`만 쓰고 뒤를 통째로 비우면 → RANGE 누적합
> `ROWS CURRENT ROW`처럼 단일 키워드만 명시하면 → 현재 행 단 1줄

`FIRST_VALUE(SAL)`은 각 행마다 지정된 윈도우 범위 내에서 가장 첫 번째 값을 가져온다.

### 2.13 그룹 함수 — ROLLUP, GROUPING SETS, GROUPING

| 함수 형태 | 집계되는 그룹 조합 | 세트 수 | 비고 |
|---|---|---|---|
| `ROLLUP(A, B)` | `(A,B)`, `(A)`, `()` | 3세트 | 계층적 소계 |
| `GROUPING SETS(A, B)` | `(A)`, `(B)` | 2세트 | 평면적 개별 집계 |
| `GROUPING SETS((A, B))` | `(A,B)` | 1세트 | 단순 GROUP BY와 동일 |
| `ROLLUP((A, B))` | `(A,B)`, `()` | 2세트 | A,B를 묶어 소계 없이 총합만 |

`ROLLUP`이나 `CUBE`처럼 계층적(상향식) 소계를 만드는 특수 함수가 아니라면, 컬럼 순서가 바뀌어도 최종 집계 조합과 결과값은 동일하다. (`GROUP BY`, `GROUPING SETS()`, `GROUPING()`)

**GROUPING() 함수**

특정 컬럼이 현재 집계 기준에 **포함되어 계산되었는지 여부를 판별**하는 함수다.

| 상황 | 컬럼 표시 상태 | 반환값 | 활용 |
|---|---|---|---|
| 그룹핑에 참여 | 실제 데이터 값 출력 | `0` | 일반 행 구분 |
| 그룹핑에서 제외 | 소계/총합으로 NULL 표시 | `1` | '소계', '전체합계' 텍스트 치환 |

| 구분 | GROUPING(ID) | GROUPING(TYPE) | 합 | 설명 |
|---|---|---|---|---|
| 일반 상세 데이터 | 0 | 0 | **0** | 둘 다 그룹핑에 참여 |
| ID별 소계 | 0 | 1 | **1** | TYPE만 빠짐 |
| TYPE별 소계 | 1 | 0 | **1** | ID만 빠짐 |
| 전체 총합계 | 1 | 1 | **2** | 둘 다 집계에서 빠짐 |

`ROLLUP`이 자동 생성한 NULL을 원래 데이터의 NULL과 구분하고 화면에 '소계', '총계'로 바꿔 보여줄 때는 다음 형태로 쓰는 것이 좋다.

```sql
CASE WHEN GROUPING(컬럼) = 1 THEN '소계' ELSE 컬럼 END
```

### 2.14 관리 구문 — DDL

**명명 규칙**

- 테이블명·컬럼명은 **반드시 문자로 시작**해야 한다.
- 벤더가 사전 정의한 예약어는 식별자로 단독 사용할 수 없다. 큰따옴표로 감싸는 경우는 예외다.
- 컬럼 정의 시 **데이터 유형(타입)은 필수 명시**다.

**ALTER TABLE — Oracle과 SQL Server의 문법 차이**

| 구분 | Oracle | SQL Server |
|---|---|---|
| 기본 문법 | `ALTER TABLE 테이블명 MODIFY (컬럼명 타입 [DEFAULT 값] [NOT NULL]);` | `ALTER TABLE 테이블명 ALTER COLUMN 컬럼명 타입 [NOT NULL];` |
| 괄호 | 사용, 쉼표로 **여러 컬럼 동시 수정 가능** | 미지원, **한 번에 1개 컬럼만** |
| DEFAULT | `MODIFY` 안에서 인라인으로 지정 | `ALTER COLUMN`에서 불가, 별도 제약조건으로 추가 |

```sql
-- Oracle
ALTER TABLE 테이블명 MODIFY (컬럼명 DEFAULT 기본값);

-- SQL Server
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건명 DEFAULT 기본값 FOR 컬럼명;
```

**제약조건 추가 — ADD를 쓰느냐 마느냐**

| 구분 | 문법 형태 | 함정 |
|---|---|---|
| `CREATE TABLE` 시 | `[CONSTRAINT 제약조건명] PRIMARY KEY (컬럼)` | **`ADD` 쓰면 문법 에러** |
| `ALTER TABLE` 시 | `ADD CONSTRAINT 제약조건명 PRIMARY KEY (컬럼)` | **`ADD` 생략하거나 `ADD COLUMN` 쓰면 에러** |

```sql
-- 생성 시: ADD 없음
CREATE TABLE EMP (
    EMPNO NUMBER(4),
    ENAME VARCHAR2(20),
    CONSTRAINT PK_EMP PRIMARY KEY (EMPNO)
);

-- 생성 후: ADD 필수 (ADD COLUMN 아님)
ALTER TABLE EMP ADD CONSTRAINT PK_EMP PRIMARY KEY (EMPNO);
```

**CTAS 제약조건 승계 규칙**

`CREATE TABLE ... AS SELECT`로 테이블을 복제할 때 뭐가 따라오고 뭐가 안 따라올까.

| 구분 | 항목 |
|---|---|
| 복제됨 | 컬럼명, 데이터 타입, 데이터 내용, **NOT NULL 제약조건** |
| 복제 안 됨 | **PRIMARY KEY**, FOREIGN KEY, UNIQUE, CHECK, DEFAULT 값 |

**객체 삭제 옵션**

| 옵션 | 동작 |
|---|---|
| `RESTRICT` | 스키마 객체 내부가 비어 있을 때만 삭제 성공 (보수적) |
| `CASCADE` | 내부/종속 객체까지 일괄 연쇄 삭제 |

### 2.17 관리 구문 — DCL의 GRANT와 ROLE

권한은 두 종류로 나뉘고, 문법이 서로 다르다.

```sql
-- 객체 권한: ON 절 필수
GRANT SELECT, INSERT ON EMP TO USER1 [WITH GRANT OPTION];

-- 시스템 권한: ON 절 없음
GRANT CREATE SESSION, CREATE TABLE TO USER1 [WITH ADMIN OPTION];
```

| 구분 | 객체 권한 | 시스템 권한 |
|---|---|---|
| `ON 객체` 절 | **반드시 사용** | **사용 안 함** (쓰면 에러) |
| 권한 예시 | `SELECT`, `INSERT`, `UPDATE` | `CREATE TABLE`, `CREATE SESSION` |
| 재부여 옵션 | `WITH GRANT OPTION` | `WITH ADMIN OPTION` |
| REVOKE 시 연쇄 취소 | **연쇄 취소 됨(CASCADE)** | 연쇄 취소 안 됨 (독립적) |

**ROLE**은 여러 권한의 묶음이다. 시스템 권한과 마찬가지로 `ON 객체` 절을 쓰지 않는다.
