## 1. ROLLUP vs GROUPING SETS — 괄호가 전부다

### 괄호 규칙은 두 함수가 똑같다

가장 헷갈렸던 부분인데, 결론부터 말하면 **괄호를 다루는 규칙 자체는 둘이 동일**하다.

| 표현 | 의미 |
|---|---|
| `A, B` | 콤마로 나열 |
| `(A), (B)` | **`A, B`와 완전히 동일**. 컬럼 하나만 괄호로 감싸는 건 아무 의미 없다 |
| `(A, B)` | 여러 컬럼을 **한 덩어리로** 묶는다. 이때만 의미가 달라진다 |

`(A)`는 그냥 `A`다. 이건 ROLLUP이든 GROUPING SETS든 마찬가지다.

### 다른 건 함수의 성격이다

| 표현 | ROLLUP | GROUPING SETS |
|---|---|---|
| `(A, B)` 나열 | (A,B), (A), () → 계층적으로 하나씩 벗겨냄 | {A}, {B} → 완전히 독립된 두 집계 |
| `((A, B))` 묶기 | (A,B), () → 중간 소계가 사라짐 | {A,B} → 조합 하나만 |

- **ROLLUP**: 계층적으로 누적하며 소계를 만든다. 괄호로 묶으면 그 안쪽을 한 단위로 봐서 중간 소계 단계를 건너뛴다.
- **GROUPING SETS**: 지정한 세트만 딱딱 만든다. 묶지 않으면 조합 자체가 생기지 않는다.

### 문제 푸는 요령

결과표를 보고 **행 개수와 NULL 패턴부터 센다.**

1. 상세 행이 몇 개인가
2. 한쪽 컬럼만 NULL인 소계 행이 있는가 (없으면 괄호로 묶은 것)
3. 전부 NULL인 총계 행이 있는가

82번은 상세 9행 + 총계 1행 = 10행에 소계가 없었으니 `ROLLUP((JOB, DEPTNO))`,
83번은 (상품ID, 월) 조합 하나만 필요했으니 `GROUPING SETS((월, 상품ID))`.
둘 다 "괄호로 같이 묶어야 원하는 조합만 나온다"는 같은 원리다.

## 2. DCL — GRANT의 ON은 언제 붙나

### 문법 구조

```sql
GRANT 권한 ON 객체 TO 사용자 [WITH GRANT OPTION];
```

- `ON 객체` = 어떤 **테이블/뷰**에 대한 권한인지 (소유자가 누군지가 아니라 대상이 뭔지)
- `TO 사용자` = 누구에게 주는지
- `WITH GRANT OPTION` = 받은 사람이 남에게 재위임 가능

### ON이 필요한 것과 아닌 것

| 구분 | 예시 | ON |
|---|---|---|
| 시스템 권한 | CREATE SESSION, CREATE TABLE | ✖︎ |
| **객체 권한** | SELECT, INSERT, UPDATE, DELETE | 🗹 **필수** |
| 롤(ROLE) | `GRANT manager_role TO B_User;` | ✖︎ |

핵심은 **"대상이 특정 객체냐 아니냐"**다. 특정 테이블을 가리키는 객체 권한만 ON이 붙고, 시스템 권한과 롤은 특정 테이블 개념이 아니라 안 붙는다.

> 92번에서 `GRANT SELECT, UPDATE TO B_User;`가 오답인 이유는 "덜 구체적이라서"가 아니다. ON이 없으면 **실행 자체가 안 되는 문법 오류**다.

### 롤 만드는 흐름

```sql
CREATE ROLE manager_role;                              -- 1. 롤 생성
GRANT SELECT, UPDATE ON A_User.TB_A TO manager_role;   -- 2. 롤에 권한 담기 (ON 있음)
GRANT manager_role TO B_User;                          -- 3. 롤 부여 (ON 없음)
```

## 3. RESTRICT vs CASCADE — 안전장치냐 통째로냐

```sql
DROP SCHEMA 스키마명 RESTRICT;   -- 비어있을 때만 삭제, 뭐라도 있으면 에러
DROP SCHEMA 스키마명 CASCADE;    -- 안에 뭐가 있든 딸린 것까지 전부 삭제
```

- **RESTRICT**: "방 안에 짐 있으면 못 치워요, 다 빼고 오세요"
- **CASCADE**: "짐이고 뭐고 통째로 다 버릴게요"

DROP TABLE, DROP USER에서도 같은 논리로 쓰인다.

**실무에선 RESTRICT가 기본값처럼 쓰인다.** 삭제는 되돌리기 어려우니까, 일단 RESTRICT로 던져서 에러 나면 "아 안에 뭐가 있구나" 확인하고, 정말 지워도 되는 게 맞을 때만 CASCADE로 간다. 모르면 RESTRICT.

## 4. 참조무결성 — 삽입 규칙과 삭제 규칙은 다른 카테고리다

여기서 제대로 낚였던 부분. RESTRICT/CASCADE와 DEPENDENT는 **아예 다른 질문에 대한 답**이다.

| 구분 | 언제의 이야기 | 종류 |
|---|---|---|
| **삽입 규칙 (Insert Rule)** | 자식에 INSERT할 때 | **Dependent**, Automatic, User-specified, No Effect |
| **삭제/갱신 규칙 (Delete Rule)** | 부모를 DELETE/UPDATE할 때 | **Restrict**, Cascade, Default, Nullify |

### 삽입 규칙 4종

- **Dependent(의존)**: 부모에 PK가 **있을 때만** 자식 입력 허용. 없으면 거부
- **Automatic(자동)**: 부모 PK가 없으면 **부모를 자동 생성**한 뒤 자식 입력
- **User-specified**: 사용자 지정 기본값으로 처리
- **No Effect**: 부모 존재 여부 안 따지고 그냥 입력 허용

113번 지문이 "부모에 PK가 없으면 자식 입력을 허용하지 않는다"였으니 **DEPENDENT**.
보기에 CASCADE, RESTRICT(삭제 규칙)를 섞어 넣어서 헷갈리게 만든 문제였다.

> 같은 "Dependent"라도 **종속 엔터티(Dependent Entity)**는 완전히 다른 개념이다.
> 그건 모델링 단계에서 식별관계/비식별관계를 구분하는 용어고, 여기 Dependent는 참조동작 규칙이다.
> 단어가 나오면 **어느 맥락인지부터** 구분하자.

## 5. 제약조건 문법 — CREATE 안에서냐 ALTER로냐

99번에서 헷갈리게 만든 게 이거다. **ADD가 붙느냐 안 붙느냐**가 갈린다.

### CREATE TABLE 안에서 (ADD 없음)

```sql
CREATE TABLE PRODUCT
( PROD_ID VARCHAR2(10) NOT NULL
, PROD_NM VARCHAR2(100) NOT NULL
, REG_DT DATE NOT NULL
, REGR_NO NUMBER(10)
, CONSTRAINT PRODUCT_PK PRIMARY KEY (PROD_ID)   -- ADD 안 씀
);
```

CREATE 안에서는 "추가"가 아니라 "정의"다. 그래서 ADD가 없다.

### ALTER로 나중에 (ADD 있음)

```sql
ALTER TABLE PRODUCT ADD CONSTRAINT PRODUCT_PK PRIMARY KEY (PROD_ID);
```

순서가 정해져 있다: `ADD` → `CONSTRAINT` → `이름` → `PRIMARY KEY` → `(컬럼)`.
`ADD PRIMARY KEY 이름 ON (컬럼)` 같은 건 존재하지 않는 문법이다.

## 6. 트랜잭션 — 일관성과 고립성의 차이

이름이 비슷해서 헷갈리는데, **축이 다르다.**

| 구분 | 일관성 (Consistency) | 고립성 (Isolation) |
|---|---|---|
| 축 | **시간** (트랜잭션 전 → 후) | **동시성** (트랜잭션 A ↔ B) |
| 지키는 것 | 무결성 제약, 비즈니스 규칙 | 다른 트랜잭션의 간섭 차단 |
| 깨지면 | 모순된 데이터 상태 | Dirty Read, Phantom Read 등 |

- **일관성**: 계좌이체 전후로 두 계좌 **잔액 합계가 같아야** 한다. 도중에 실패하면 롤백해서 원상복구.
- **고립성**: A가 조회하는 동안 B가 입금 중이면, A는 B의 **커밋 안 된 중간 상태를 보면 안 된다.**

도서관 비유:
- 일관성 = 대출장부와 실제 책장의 책 개수가 항상 맞아야 한다
- 고립성 = 두 사람이 동시에 같은 책을 빌릴 때 "빌리는 중" 상태가 서로에게 보이면 안 된다

## 7. AUTO COMMIT — Oracle과 SQL Server가 정반대인 이유

### 기본 동작

| | Oracle | SQL Server |
|---|---|---|
| 기본 AUTOCOMMIT | **FALSE** (묵시적 트랜잭션) | **TRUE** |
| DML | 수동 COMMIT 필요 | 문장마다 즉시 자동 커밋 |
| DDL | **설정 무시하고 무조건 강제 커밋** | 그냥 현재 트랜잭션 모드를 따름 |

### 핵심 한 줄

> **Oracle의 DDL은 "특별대우"를 받아 설정을 무시하고 항상 즉시 확정된다.
> SQL Server의 DDL은 "평범한 문장"이라 그때그때 트랜잭션 모드를 그대로 따른다.**

그래서 SQL Server는 이게 된다:

```sql
BEGIN TRANSACTION;
CREATE TABLE TestTable (ID INT);  -- 자동 커밋 안 됨, 트랜잭션 안에 머묾
ROLLBACK;                          -- CREATE TABLE도 취소됨. Oracle이면 불가능
```

### 기본서와 노랭이가 다르게 보였던 이유

- 기본서: "기본 설정(AUTOCOMMIT=TRUE) 상태에서 DDL도 자동 커밋된다" → 맞음
- 노랭이: "SQL Server는 DDL이라고 Oracle처럼 강제 커밋시키지 않는다" → 이것도 맞음

**둘은 다른 질문에 답한 것**이다. 시험 포인트는 노랭이 쪽, 즉 **"SQL Server는 명시적 트랜잭션에서 DDL 롤백이 가능하다"**이다.

### 왜 설계가 다른가

- **Oracle**: 데이터 딕셔너리를 모든 세션이 공유하니, DDL을 롤백 가능하게 하면 "있던 테이블이 갑자기 사라지는" 혼란이 생긴다. 그래서 **아예 롤백 불가로 못 박아** 복잡성을 원천 차단했다. 안정성과 단순성을 택함.
- **SQL Server**: 시스템 카탈로그도 일반 테이블처럼 취급해서 DDL도 트랜잭션 로그를 탄다. 대신 스키마 락 같은 복잡한 잠금 체계가 필요하다. 유연성(스키마 변경 되돌리기)을 택함.

## 8. MERGE INTO — INSERT와 UPDATE를 한 방에

```sql
MERGE INTO A          -- 바뀔 대상 테이블
USING B               -- 비교 기준이 될 데이터
ON (A.컬럼 = B.컬럼)   -- 매칭 조건 (보통 PK)
WHEN MATCHED THEN
    UPDATE SET ...    -- 이미 있으면 갱신
WHEN NOT MATCHED THEN
    INSERT ...;       -- 없으면 삽입
```

엑셀로 치면 **원본 시트에 새 데이터 시트를 대조해서, 있는 건 덮어쓰고 없는 건 추가**하는 자동 병합이다. INSERT/UPDATE 판단을 직접 안 해도 되게 만들어준다.

## 9. 키(Key) 총정리

```
슈퍼키 (유일성 O, 최소성 X)
  └ 후보키 (유일성 O, 최소성 O)
       ├ 기본키(PK)  → SQL: PRIMARY KEY 제약 (NOT NULL + UNIQUE)
       └ 대체키       → SQL: UNIQUE 제약 (NULL 허용)

외래키(FK) = 다른 테이블 PK 참조, 관계를 만드는 연결고리
자연키 vs 대리키(인조식별자) = 키를 "어디서 가져왔냐"의 구분
```

### 각각 정리

- **슈퍼키**: 유일성만 만족. 최소성은 없어도 된다. `(학번, 이름)`처럼 군더더기가 껴 있어도 슈퍼키.
- **후보키**: 유일성 + 최소성. 하나라도 빼면 유일성이 깨져야 한다.
- **기본키**: 후보키 중 대표 하나. NOT NULL, 테이블당 1개.
- **대체키**: 후보키인데 기본키로 안 뽑힌 나머지.
- **외래키**: 다른 테이블 PK를 참조. 자기 테이블에선 PK일 수도 아닐 수도 있다.
- **대리키(인조식별자)**: 자연키가 마땅찮을 때 인위적으로 만든 순번/시퀀스. 안 바뀌고 단순해서 조인 성능도 좋다.

> "모든 후보키는 슈퍼키지만, 모든 슈퍼키가 후보키는 아니다."

### PK vs UNIQUE

| | PRIMARY KEY | UNIQUE |
|---|---|---|
| NULL | ✖︎ 불가 | 🗹 허용 |
| 개수 | 테이블당 1개 | 여러 개 가능 |
| 역할 | 기본키 구현 | **대체키 구현** |

UNIQUE는 이론상의 "대체키"를 실제 SQL로 구현하는 수단이다.

## 10. 식별관계 연쇄 — 속성 개수 세는 법

### 구조

```
회원(회원ID)
   ↓ 식별관계
회원연락처(회원ID + 구분코드)          ← 부모 PK를 자기 PK 일부로 상속
   ↓ 식별관계
회원연락처이력(회원ID + 구분코드 + α)   ← 부모 PK 전체를 상속
```

### 공식

**n레벨 엔터티의 PK = (부모 PK 전체) + (이 레벨의 판별자)**

**최소 속성 개수 = 누적된 식별자 개수 + 그 레벨의 일반속성 개수**

### 시험용 감각

매 단계 이 질문만 던지면 된다:

1. 부모 PK 몇 개 물려받았나?
2. **부모 PK만으로 이 자식 데이터가 겹칠 수 있나?**
   - 겹친다(1:N, 특히 **이력·변경·로그류**) → 판별자 +1 필요
   - 안 겹친다(1:1) → +0
3. 이 레벨 일반속성 개수 더하기

10번 문제: 상속 식별자 2개(회원ID, 구분코드) + 유일성용 추가 1개 + 일반속성 3개 = **최소 6개**.
이력 엔터티는 같은 조합에 여러 건이 쌓이는 게 본질이라 **판별자가 사실상 필수**다.

> 이 문제의 정답은 ②번. 식별관계라서 부모(회원ID + 구분코드)를 참조해야만 INSERT가 가능한데,
> "독립적인 트랜잭션에서 개별 INSERT 가능"이라고 했으니 틀렸다.

## 11. CRUD 매트릭스와 데이터 독립성

### CRUD 매트릭스

프로세스(행) × 엔터티(열)에 C/R/U/D를 표시해서, **어떤 업무가 어떤 테이블을 어떻게 건드리는지** 한눈에 보는 설계 검증 문서다. 인덱스와는 아무 상관 없다 — 인덱스는 성능 도구, 이건 설계 문서다.

이걸로 확인하는 것:
- 어떤 프로세스에서도 안 쓰이는 테이블은 없나 (불필요한 테이블)
- 프로세스가 필요한 테이블에 다 접근하나 (설계 누락)
- 한 테이블에 CRUD가 과하게 몰려있지 않나 (변경 리스크 지점)

### 데이터 독립성 — 프로그래밍 원칙과 같은 얘기

> "프로그램과 테이블 간의 연계성을 높이는 것은 데이터 모델이 업무 변경에 취약해지는 단점"

이게 왜 단점인지는 소프트웨어 공학의 **결합도(Coupling)** 개념 그대로다.

| 프로그래밍 | 데이터 모델링 |
|---|---|
| 특정 기능에 종속된 함수는 재사용 불가 | 특정 화면에 종속된 테이블은 다른 프로세스에 못 씀 |
| 모듈화 → 다른 프로젝트로 이식 가능 | 데이터 독립성 → 새 프로그램이 붙어도 안정적 |
| 강한 결합 → 하나 고치면 연쇄 수정 | 연계성 과다 → 하나 바꾸면 연쇄 수정 |

특정 장표에 맞춰 테이블을 설계하면 당장은 편하지만, 그 화면이 개편되는 순간 테이블까지 뜯어고쳐야 한다. 잘 설계된 API처럼 **누가 갖다 써도 되는 범용 자산**으로 만드는 게 목표다.

> **데이터 모델은 업무의 본질(엔터티-관계)에 집중해야지, 특정 프로세스에 종속되면 안 된다.**

## 12. SQL 논리적 실행 순서 — 숲 보는 법

순서를 **외우는 것**과 문제에 **적용하는 것**은 다른 스킬이다. 손으로 재배열해보는 연습이 따로 필요하다.

```
① FROM     → 어떤 테이블에서 시작하나
② WHERE    → 그룹핑 전, 행 단위로 거르는 조건
③ GROUP BY → 무엇을 기준으로 여러 행을 하나로 압축하나
④ HAVING   → 압축된 후, 집계함수로 그룹을 거르는 조건
⑤ SELECT   → 최종적으로 보여줄 열
```

### 체크리스트

1. **FROM**: 테이블 몇 개? 조인인가?
2. **WHERE**: 여기서 "조인조건"과 "진짜 필터조건"을 구분했나?
3. **GROUP BY**: 뭘 기준으로 뭉쳤나? (이 순간부터 "그룹" 단위로 사고 전환)
4. **HAVING**: **어떤 집계함수**로 걸렀나? ← 실수가 가장 많이 나오는 지점
5. **SELECT**: HAVING의 함수와 SELECT의 함수가 **같은 함수인지 대조**

### 19번의 함정

```sql
SELECT 고객이름, 상품, SUM(수량)   -- 보여주는 건 SUM
...
HAVING MAX(수량) > 10              -- 거르는 건 MAX
```

`HAVING MAX(수량) > 10`은 "한 번이라도 10개 초과 주문한 적이 있는" 그룹을 남긴다. SELECT의 SUM은 그냥 출력값일 뿐, 조건과 무관하다. **"합이 10보다 크다"고 착각하게 만드는 함정.**

## 13. 연관 vs 비연관 서브쿼리

### 진짜 기준은 실행 순서가 아니다

| 구분 | 판단 기준 | 결과로 나오는 실행 순서 |
|---|---|---|
| **비연관** | 메인쿼리 컬럼을 **참조 안 함** | 서브 → 메인 (한 번 실행) |
| **연관** | 메인쿼리 컬럼을 **참조함** | 메인 → 서브 (행마다 재실행) |

실행 순서는 **결과로 관찰되는 현상**이고, 실제로 봐야 할 건 **"서브쿼리 안에 바깥 테이블 컬럼이 등장하는가"**다.

### 두 축은 서로 독립적이다

서브쿼리 분류 축이 두 개인데 서로 직교한다.

1. **위치·결과 모양**: 스칼라 / 인라인뷰 / 단일행 / 다중행 / 다중컬럼
2. **아우터 참조 여부**: 연관 / 비연관

**어떤 타입이든 연관도 되고 비연관도 된다.**

| 타입 | 비연관 | 연관 |
|---|---|---|
| 스칼라 | `(SELECT AVG(급여) FROM EMP)` | `(SELECT COUNT(*) FROM ORDERS O WHERE O.고객ID = E.고객ID)` |
| 단일행 | `WHERE 급여 > (SELECT AVG(급여) FROM EMP)` | `WHERE 급여 > (SELECT AVG(급여) FROM EMP E2 WHERE E2.부서ID = E.부서ID)` |
| 다중행 | `WHERE 부서ID IN (SELECT 부서ID FROM DEPT WHERE 지역='서울')` | `WHERE EXISTS (SELECT 1 FROM ORDERS O WHERE O.고객ID = E.고객ID)` |

### 유일한 예외: 인라인뷰

FROM절 서브쿼리는 바깥 컬럼을 참조할 방법이 없다. 그래서 **항상 비연관**이고, 항상 "서브 먼저 실행 → 가상 테이블 → 메인이 조인" 순서다.

## 마무리 — 시험장에서 쓸 압축 요령

1. **ROLLUP/GROUPING SETS**: 결과표의 **행 개수와 NULL 패턴**부터 센다
2. **GRANT**: SELECT/UPDATE 같은 객체 권한이면 **ON 없으면 무조건 오답**
3. **RESTRICT/CASCADE vs DEPENDENT**: "삭제할 때"인지 "입력할 때"인지 **지문의 시점**을 먼저 본다
4. **제약조건**: CREATE 안이면 ADD 없음, ALTER면 ADD CONSTRAINT
5. **AUTO COMMIT**: "Oracle의 DDL만 특별대우" 한 줄로 정리
6. **식별관계**: 이력 엔터티 나오면 **판별자 +1** 거의 확정
7. **복잡한 SQL**: FROM→WHERE→GROUP BY→HAVING→SELECT로 **손으로 재배열**
8. **서브쿼리**: 안에 바깥 컬럼 있나 없나만 본다

범위가 좁아 보여도 세부 규칙이 계속 나오는 게 SQLD다. 예외를 다 외우려 하지 말고 **원리를 잡으면** 처음 보는 변형도 유추가 된다.
