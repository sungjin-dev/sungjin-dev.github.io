# 정보처리기사 실기 이론 압축 요약 


<br>

### 먼저 읽어 두면 좋은 것

정처기 실기는 범위가 넓다. 그렇다면 어디서부터 시작해야 할까? 출제 비중이 큰 곳부터 뼈대를 잡는 것이 가장 효율적이다.

물론 기출 문제만 반복해서 풀어도 합격선에는 닿을 수 있다. 하지만 이론의 뼈대가 없으면 문제가 한 번만 비틀려도 막힌다. 이 글은 그 뼈대를 표와 그림으로 압축한 요약본이다.

표기 규칙은 다음과 같다.

| 표시 | 의미 |
|---|---|
| ★ | 핵심. 가장 먼저 외운다 |
| ◆ | 보조. 핵심 다음에 본다 |
| ◇ | 후순위. 시간이 남으면 본다 |
| ▲ | 시험에 자주 나오는 키워드 |
| † | 원본 요약 자료에서 끊기거나 빠져 있어 보충한 항목 |

※ 보충(†) 항목은 일반적인 정처기 출제 범위를 기준으로 추론해 채웠다. 시험 직전에 교재나 기출로 한 번 더 대조하는 것이 좋다.

<br>

### 목차

- 0. 요약 범위
- 1부. 데이터베이스 (SQL 포함)
- 2부. 네트워크 · 운영체제
- 3부. SW 개발
- 4부. SW 설계 (Java 객체지향 포함)
- 5부. 보안 · 신기술

### 2) 트랜잭션 ◆

은행 이체를 떠올리면 쉽다. 내 계좌에서 돈이 빠졌는데 상대 계좌에 들어가지 않았다면 어떻게 될까? 이 두 작업을 한 덩어리로 묶는 것이 트랜잭션이다. 즉, DB 상태를 바꾸는 논리적 작업 단위다.

**(1) ACID 특성 †**

| 특성 | 영어 | 핵심 키워드 |
|---|---|---|
| 원자성 ▲ | Atomicity | **All or Nothing**. 전부 수행되거나 전부 취소 |
| 일관성 ▲ | Consistency | 실행 전후로 DB 상태가 일관되게 유지 |
| 격리성 ▲ | Isolation | 실행 중인 트랜잭션에 다른 트랜잭션이 간섭하지 못함 |
| 영속성(지속성) ▲ | Durability | 완료된 결과는 영구적으로 반영 |

**(2) 회복 기법 종류**

| 기법 | 종류 | 키워드 |
|---|---|---|
| 로그 기반 회복 | **지연 갱신** | 트랜잭션 완료까지 DB 변경을 지연. **Redo만** 사용 |
| 로그 기반 회복 | **즉각 갱신** | 즉시 DB에 반영. **Redo, Undo 모두** 사용 |
| 체크포인트 회복 | | 특정 시점(체크포인트)의 DB 상태를 저장해 두고, 장애 발생 시 그 체크포인트로 회복 |
| 그림자 페이징 | | 원본 복사본(그림자 페이지)을 만들고, 트랜잭션이 실패하면 그림자 페이지로 대체 |

**(3) 동시성 제어 ▲**

| 제어 방법 | 키워드 |
|---|---|
| **Locking(로킹)** | 트랜잭션의 순차적 진행을 보장하는 직렬화 기법. 잠그면 다른 트랜잭션은 접근 불가 |
| **S-Lock(공유 락)** | 데이터를 읽을 때 사용. 읽기는 여러 트랜잭션이 동시에 가능, 쓰기는 불가 |
| **X-Lock(배타 락)** | 데이터를 쓸(write) 때 사용. 다른 트랜잭션은 읽기/쓰기 모두 불가 |
| 2PL(2단계 로킹) † | 확장 단계(락 획득만) → 축소 단계(락 해제만). 직렬성 보장 |

**(4) 트랜잭션 상태 †**

| 상태 | 설명 |
|---|---|
| 활동(Active) | 연산을 실행 중 |
| 부분 완료(Partially Committed) | 마지막 연산까지 실행, 아직 DB에 반영 전 |
| 완료(Committed) | Commit 연산 성공. 영구 반영 |
| 실패(Failed) | 오류로 더 이상 진행 불가 |
| 철회(Aborted) | Rollback 후 트랜잭션 시작 전 상태로 복귀 |

### 3) 관계대수 / 관계해석 ★

두 언어는 같은 질문을 다른 방식으로 묻는다. 관계대수는 "어떻게 가져올지" 순서를 적고, 관계해석은 "무엇을 원하는지"만 적는다.

**(1) 관계대수란?**

| 관계대수 | 관계해석 ▲ |
|---|---|
| 절차적 언어 | 비절차적 언어 (Codd 박사 제안) |
| 어떻게(HOW) 데이터를 가져올 것인지 명시 | 무엇을(WHAT) 원하는지만 명시 |

관계해석에는 튜플 관계해석, 도메인 관계해석 두 종류가 있고 † 한정자로 전칭 한정자 ∀(모든), 존재 한정자 ∃(존재)를 쓴다.

**(2) 일반 집합 연산자**

| 연산자 | 기호 | 설명 |
|---|---|---|
| 합집합 ▲ | ∪ | 중복 제외, 두 릴레이션 튜플 모두 반환 |
| 교집합 ▲ | ∩ | 두 릴레이션 공통 튜플만 반환 |
| 차집합 ▲ | − | 왼쪽 릴레이션에 속하면서 오른쪽 릴레이션에 속하지 않는 튜플 반환 |
| 카티션 프로덕트 ▲ | × | 두 릴레이션의 튜플들을 순서쌍으로 조합해 만들 수 있는 모든 튜플 반환 |

**(3) 순수 관계 연산자**

| 연산자 | 기호 | 설명 |
|---|---|---|
| 셀렉트(Select) | σ(Sigma) | 주어진 조건을 만족하는 튜플 반환 (수평) |
| 프로젝트(Project) | π(Pi) | 주어진 조건을 만족하는 열 반환 (수직) |
| 조인(Join) | ⋈ | 두 릴레이션 공통 속성 기준 결합 |
| 디비전(Division) | ÷ | A÷B : B의 모든 튜플에 대해 관계를 맺고 있는 A의 튜플만 반환 |

주어진 릴레이션에 연산자를 적용한 결과를 직접 쓰는 문제가 나오므로, 아래 예시를 손으로 한 번씩 풀어 보는 것이 좋다.

**셀렉트(σ). 조건에 맞는 행만 남긴다**

연산: σ<sub>학년=3</sub>(학생)

| 이름 | 학년 |
|---|---|
| 김감자 | 3 |
| 이고구마 | 2 |
| 박옥수수 | 3 |

결과: 학년이 3인 튜플만 반환한다.

| 이름 | 학년 |
|---|---|
| 김감자 | 3 |
| 박옥수수 | 3 |

**프로젝트(π). 필요한 열만 뽑고 중복을 제거한다**

연산: π<sub>학생</sub>(수강)

| 학생 | 과목 |
|---|---|
| 김감자 | DB |
| 김감자 | 네트워크 |
| 이고구마 | DB |
| 박옥수수 | DB |
| 박옥수수 | 네트워크 |

결과: 학생 열만 남기고 중복을 지운다. 김감자, 이고구마, 박옥수수.

**디비전(÷). B의 모든 값과 짝이 있는 A만 남긴다**

연산: 수강 ÷ 필수과목 → 필수과목을 모두 수강한 학생

| 필수과목 |
|---|
| DB |
| 네트워크 |

결과: DB와 네트워크를 **모두** 수강한 학생만 남는다. 김감자, 박옥수수. 이고구마는 DB만 들었으므로 제외된다.

### 4) 관계 데이터 모델 ★

| 구성요소 | 키워드 |
|---|---|
| **Attribute(속성)** ▲ | 릴레이션의 각 **열(Column)**. 파일 구조상 데이터 필드 |
| **Tuple(튜플)=Record** ▲ | 릴레이션의 각 **행(Row)**. 중복 포함 불가 |
| **Cardinality(카디널리티)** ▲ | 튜플(Row)의 개수. 릴레이션의 **행 개수** |
| **Degree(차수)** ▲ | 속성(Attribute)의 개수. 릴레이션의 **열 개수** |
| **Domain(도메인)** ▲ | 하나의 속성이 가질 수 있는 **값들의 집합** |
| **Relation Instance** (릴레이션 인스턴스) | = Relation Extension(릴레이션 외연). 특정 시점의 릴레이션에 들어 있는 실제 데이터 집합 |
| **Relation(릴레이션, 테이블)** ▲ | 행과 열로 구성된 2차원 데이터 집합(표) 자체 |
| **Relation Schema** (릴레이션 스키마) | DB 구조(제약 조건 명세. 이름, 속성, 타입 등 정의) |
| **Identifier(식별자)** ▲ | 각 튜플을 고유하게 식별하는 속성 (예: 후보키) |

릴레이션 하나로 구성요소를 한눈에 보면 이렇다.

| 학번 (식별자) | 이름 | 학년 |
|---|---|---|
| 1 | 감자 | 3 |
| 2 | 고구마 | 2 |
| 3 | 옥수수 | 1 |

- 열(속성)이 3개이므로 **차수 = 3**
- 행(튜플)이 3개이므로 **카디널리티 = 3**

### 6) 정규화 ◇

이삿짐을 싸는 일에 빗댈 수 있다. 책, 옷, 주방용품을 한 상자에 뒤섞으면 이사 후에 찾기 어렵다. 정규화는 데이터를 성격별 상자(테이블)로 나눠 중복과 이상 현상을 줄이는 작업이다.

**(1) 정규형 ▲**

| 정규형 | 조건 |
|---|---|
| 제1정규형 ▲ | 모든 속성 값 = 원자값(Atomic value) |
| 제2정규형 ▲ | 부분 함수 종속 제거 (완전 함수 종속 성립) |
| 제3정규형 ▲ | 이행 함수 종속 제거 |
| BCNF ▲ | 모든 결정자가 후보키 |
| 제4정규형 ▲ | 다치 종속 제거 |
| 제5정규형 ▲ | 조인 종속 제거 |

**(2) 함수 종속성**

A → B는 "속성 A의 값이 속성 B의 값을 결정한다"는 뜻이다.

| 함수 종속성 | 설명 |
|---|---|
| **완전 함수 종속** ▲ | 기본키 전체에 대해서만 종속 |
| **부분 함수 종속** ▲ | 기본키의 일부 속성에 종속 |
| **이행 함수 종속** ▲ | A → B, B → C일 때 A → C가 성립. 후보키에 포함되지 않은 속성이 다른 후보키에 포함되지 않은 속성을 결정하는 경우 |

이행 함수 종속의 예로 학번 → 학과, 학과 → 학과장이면 학번 → 학과장이 성립한다. †

**반정규화 ▲**: 정규화된 테이블 구조를 의도적으로 통합, 분리하거나 중복을 허용하는 것. 목적은 성능 최적화다.

<br>

### 7) 이상 현상 ◇

| 이상 현상 | 핵심 키워드 | 설명 |
|---|---|---|
| **삽입 이상** (Insertion) | 불필요한 데이터 없이는 새 데이터를 삽입할 수 없음 | 필요 없는 값까지 강제로 넣어야 함 |
| **삭제 이상** (Deletion) | 한 튜플 삭제 시 **다른 데이터까지 삭제** | 정보 손실 |
| **갱신 이상** (Update) | 중복 데이터 일부만 수정되어 값이 서로 불일치 | 같은 정보가 여러 곳에 있을 때 발생 |

<br>

### 8) 키(Key) ◆

| 키 종류 | 핵심 키워드 |
|---|---|
| **기본키** | 후보키 중 선택된 키, NOT NULL |
| **대체키** | 후보키 중 나머지 선택되지 못한 키 |
| **후보키** | **유일성** ▲, **최소성** ▲ 모두 만족. 튜플을 구별하는 데 기준이 되는 키 |
| **슈퍼키** | **유일성** ▲ 만족, **최소성** ✕. 튜플을 유일하게 식별 |
| **외래키** | 한 릴레이션의 컬럼이 다른 릴레이션의 기본키 |

기억 공식은 기본키 + 대체키 = 후보키 ⊂ 슈퍼키다.

<br>

### 9) 스토리지 (RAID) ◇

| RAID | 핵심 | 키워드 |
|---|---|---|
| RAID 0 | 분산 저장(**스트라이핑**) | 스트라이핑(Striping), 패리티 없음, 복제 없음 |
| RAID 1 | 복제 저장(**미러링**) | 미러링(Mirroring), 디스크 2개에 같은 데이터 복제 |
| RAID 5 | 스트라이핑 + 분산 패리티 | 패리티(오류 검출 + 복구 가능), 데이터 분산 저장. 패리티 분산 저장으로 성능·안정성 균형, 최소 3개 디스크 |
| RAID 6 | 스트라이핑 + 이중 분산 패리티 | 독립적인 두 개의 패리티를 분산 저장, 최소 4개 디스크 |
| RAID 10 | 미러링 후 스트라이핑 | RAID 1 + RAID 0, 최소 4개 디스크, 높은 성능 + 높은 안정성 |

<br>

### 10) 무결성 ◇

| 무결성 | SQL 구현 | 키워드 |
|---|---|---|
| **개체 무결성** | PRIMARY KEY | 기본키 = NOT NULL + 유일 |
| **참조 무결성** | FOREIGN KEY | 외래키 = 참조 테이블의 기본키 값 or NULL |
| **도메인 무결성** † | DOMAIN, CHECK, 데이터 타입 | 속성 값이 정의된 도메인 범위 안에 있어야 함 |

<br>

### 11) 파일 구조 †  ◇

| 파일 구조 | 키워드 |
|---|---|
| 순차 파일 | 레코드를 입력 순서(키 순서)대로 저장. 접근이 느리지만 구조가 단순 |
| 인덱스 순차 파일 (ISAM) | 인덱스 + 순차 저장. 인덱스로 빠른 직접 접근, 순차 처리도 가능 |
| 직접(해싱) 파일 | 해시 함수로 저장 주소를 계산. 빠르지만 충돌(Collision) 처리 필요 |
| B-Tree / B+Tree | 균형 트리 인덱스. B+Tree는 리프 노드끼리 연결되어 범위 검색에 유리 |

## 부록. SQL 기초 (DDL · DML · DCL)

SQL은 DML(데이터 조작어)이 가장 비중이 크다. 그래서 DML을 먼저 자세히 보고, 나머지는 문법 틀만 정리한다.

<br>

### 1) DDL · 데이터 정의어 †

| 명령 | 역할 | 형태 |
|---|---|---|
| CREATE | 테이블 생성 | `CREATE TABLE 테이블 (컬럼 타입 제약조건, ...);` |
| ALTER | 구조 변경 | `ALTER TABLE 테이블 ADD 컬럼 타입;` / `MODIFY` / `DROP COLUMN` |
| DROP | 테이블 삭제 | `DROP TABLE 테이블 [CASCADE \| RESTRICT];` |
| TRUNCATE | 데이터만 전체 삭제(구조 유지) | `TRUNCATE TABLE 테이블;` |

```sql
CREATE TABLE 학생 (
  학번     INT PRIMARY KEY,
  이름     VARCHAR(20) NOT NULL,
  학과코드 CHAR(2),
  FOREIGN KEY (학과코드) REFERENCES 학과(학과코드)
);
```

<br>

### 2) DML · 데이터 조작어 ★ 기초

**데이터 관련**

| 상황 | 쿼리 |
|---|---|
| 데이터 추가 ▲ | `INSERT INTO 테이블명(컬럼1, 컬럼2...) VALUES (값1, 값2 ...);` (컬럼 생략 가능) |
| 데이터 복사 | `INSERT INTO 테이블명(컬럼1, 컬럼2...) SELECT 컬럼3, 컬럼4... FROM 테이블2;` |
| 데이터 삭제 ▲ | `DELETE FROM 테이블 WHERE 조건;` |
| 데이터 수정 ▲ | `UPDATE 테이블 SET 컬럼1 = 값1, 컬럼2 = 값2 WHERE 조건;` |

**정렬 관련**

```sql
-- 컬럼 기준 정렬
SELECT 컬럼1, 컬럼2 FROM 테이블 ORDER BY 컬럼1 ASC;   -- 오름차순 (생략 가능)
SELECT 컬럼1, 컬럼2 FROM 테이블 ORDER BY 컬럼1 DESC;  -- 내림차순

-- 두 개 컬럼 정렬: 앞에 쓴 컬럼이 먼저 정렬된다
SELECT 컬럼1, 컬럼2 FROM 테이블 ORDER BY 컬럼1 DESC, 컬럼2 DESC;  -- 컬럼1 먼저
SELECT 컬럼1, 컬럼2 FROM 테이블 ORDER BY 컬럼2 DESC, 컬럼1 DESC;  -- 컬럼2 먼저
```

**조회 관련**

```sql
-- 범위 조회
SELECT 컬럼1, 컬럼2 FROM 테이블 WHERE 컬럼1 BETWEEN 1 AND 3;  -- 1~3 사이
SELECT 컬럼1, 컬럼2 FROM 테이블 WHERE 컬럼1 IN (1, 2, 3);     -- 1, 2, 3 중 하나

-- 특정 문자로 시작 / 포함 / 앞에 딱 한 글자
SELECT 컬럼1 FROM 테이블 WHERE 컬럼1 LIKE '특정문자%';
SELECT 컬럼1 FROM 테이블 WHERE 컬럼1 LIKE '%특정문자%';
SELECT 컬럼1 FROM 테이블 WHERE 컬럼1 LIKE '_특정문자';

-- 합계에 조건을 걸어 조회
SELECT 컬럼2, SUM(컬럼1) AS 합계 FROM 테이블
WHERE 조건 GROUP BY 컬럼2 HAVING SUM(컬럼1) > 100;
```

**LIKE 와일드카드**

| 기호 | 의미 | 예시 | 매칭 |
|---|---|---|---|
| `%` | 0글자 이상 아무 문자 | `LIKE '감자%'` | 감자, 감자집 (감자로 시작) |
| `%` | 0글자 이상 아무 문자 | `LIKE '%감자%'` | 왕감자집 (중간에 감자 포함) |
| `_` | 딱 한 글자 | `LIKE '_감자'` | 왕감자 (앞에 한 글자 + 감자) |

**NULL · 별칭 관련**

```sql
SELECT 컬럼1, 컬럼2 FROM 테이블 WHERE 컬럼1 IS NULL;       -- NULL은 = 이 아니라 IS NULL
SELECT 컬럼1 AS 별칭1, 컬럼2 AS 별칭2 FROM 테이블;          -- AS는 생략 가능
```

**집계 함수 ▲**

| 집계 함수 | 키워드 |
|---|---|
| `COUNT(*, 컬럼명)` ▲ | `*` : **모든** 행의 개수 / 컬럼명 : 컬럼이 **NULL이 아닌** 행의 개수 |
| `SUM(컬럼명)` | 컬럼명에 있는 값의 **합계** |
| `AVG(컬럼명)` | 컬럼명에 있는 값의 **평균** |
| `MAX(컬럼명)` | 컬럼명에 있는 값 중 **최대값** |
| `MIN(컬럼명)` | 컬럼명에 있는 값 중 **최소값** |

```sql
SELECT COUNT(컬럼명) FROM 테이블 WHERE 조건;  -- 조건을 만족하는 행 중 컬럼명이 NULL이 아닌 행의 개수
```

WHERE와 HAVING을 헷갈리는 경우가 많다. WHERE는 그룹으로 묶기 **전** 행을 거르고, HAVING은 묶은 **후** 그룹을 거른다. †

<br>

### 3) 조인(JOIN) ▲

조인 예제는 아래 두 테이블로 통일한다.

**학생**

| 학번 | 학과코드 |
|---|---|
| 1 | D1 |
| 2 | D2 |
| 3 | D9 |

**학과**

| 학과코드 | 학과명 |
|---|---|
| D1 | 컴퓨터 |
| D2 | 전자 |
| D3 | 기계 |

**동등조인 · INNER JOIN ▲**

```sql
SELECT * FROM 학생
INNER JOIN 학과 ON 학생.학과코드 = 학과.학과코드;
```

| 학번 | 학과코드 | 학과코드 | 학과명 |
|---|---|---|---|
| 1 | D1 | D1 | 컴퓨터 |
| 2 | D2 | D2 | 전자 |

ON 조건에서 공통 컬럼이 **일치하는** 튜플만 반환한다. INNER는 생략할 수 있다. 세타조인에서 조건이 `=`인 경우가 동등조인이다.

**자연조인 · NATURAL JOIN ▲**

```sql
SELECT * FROM 학생 NATURAL JOIN 학과;
```

| 학번 | 학과코드 | 학과명 |
|---|---|---|
| 1 | D1 | 컴퓨터 |
| 2 | D2 | 전자 |

동등조인과 결과는 같지만 공통 컬럼(학과코드)이 **1번만** 남는다. ON 없이 같은 이름의 컬럼으로 자동 조인한다.

**외부조인 · OUTER JOIN ▲**

```sql
SELECT * FROM 학생
LEFT OUTER JOIN 학과 ON 학생.학과코드 = 학과.학과코드;
```

| 학번 | 학과코드 | 학과코드 | 학과명 |
|---|---|---|---|
| 1 | D1 | D1 | 컴퓨터 |
| 2 | D2 | D2 | 전자 |
| 3 | D9 | NULL | NULL |

| 종류 † | 의미 |
|---|---|
| LEFT OUTER JOIN | 왼쪽 테이블은 모두 반환. 짝이 없으면 오른쪽을 NULL로 채움 |
| RIGHT OUTER JOIN | 오른쪽 테이블은 모두 반환. 짝이 없으면 왼쪽을 NULL로 채움 (위 예제에서는 D3 기계 행이 추가됨) |
| FULL OUTER JOIN | 양쪽 모두 반환. 짝이 없는 쪽은 NULL |

| 구분 | 명령 | 형태 |
|---|---|---|

### 1) 메모리 ◇

**(1) 가상 메모리와 단편화 †**

| 용어 | 키워드 |
|---|---|
| 가상 메모리 | 보조기억장치 일부를 주기억장치처럼 사용해 실제 메모리보다 큰 프로그램 실행 |
| 페이징 | 고정 크기(페이지)로 분할. **내부 단편화** 발생 가능 |
| 세그먼테이션 | 논리 단위의 가변 크기(세그먼트)로 분할. **외부 단편화** 발생 가능 |
| 스래싱(Thrashing) | 페이지 부재가 너무 잦아 실제 작업보다 교체에 시간을 더 쓰는 현상 |

**(2) 메모리 배치 전략 †**

| 전략 | 키워드 |
|---|---|
| First Fit (최초 적합) | 들어갈 수 있는 첫 번째 공간에 배치 |
| Best Fit (최적 적합) | 들어갈 수 있는 공간 중 **가장 작은** 공간에 배치 |
| Worst Fit (최악 적합) | 들어갈 수 있는 공간 중 **가장 큰** 공간에 배치 |

**(3) 페이지 교체 알고리즘 ▲**

메모리 프레임이 가득 찼을 때 어떤 페이지를 내보낼까? 이 질문에 대한 답이 알고리즘마다 다르다.

| 알고리즘 | 내보내는 기준 |
|---|---|
| **FIFO** ▲ | 가장 먼저 들어온 페이지 |
| **LRU** ▲ | 가장 오랫동안 참조되지 않은 페이지 |
| **LFU** ▲ | 참조 횟수가 가장 적은 페이지 |
| OPT † | 앞으로 가장 오래 사용되지 않을 페이지 (이론상 최적, 구현 불가) |
| NUR † | 참조 비트와 변경 비트를 보고 최근 사용하지 않은 페이지 |

**문제.** 3개 프레임, 페이지 참조 순서 `2, 3, 2, 1, 5, 2, 4`일 때 Page Fault는 몇 번인가? (V = Page Fault)

**FIFO ▲. 밀어내기 식으로 푼다**

1. 밀어내기 식으로 푼다.
2. 이전에 있던 페이지 참조 시 **순서를 유지**한다.
3. 이전 메모리에 참조하는 페이지가 있었는지 확인하면서 Page Fault를 체크한다.

| 참조 | 2 | 3 | 2 | 1 | 5 | 2 | 4 |
|---|---|---|---|---|---|---|---|
| 1 프레임 | 2 | 2 | 2 | 2 | 5 | 5 | 5 |
| 2 프레임 | - | 3 | 3 | 3 | 3 | 2 | 2 |
| 3 프레임 | - | - | - | 1 | 1 | 1 | 4 |
| Page Fault | V | V | - | V | V | V | V |

**답: 6**

**LRU ▲. 가장 오랫동안 참조되지 않은 페이지를 내보낸다**

1. 밀어내기 식으로 푼다.
2. 이전에 있던 페이지를 참조하면 그 페이지를 **위로(최근으로)** 올린다.
3. 이전 메모리에 참조하는 페이지가 있었는지 확인하면서 Page Fault를 체크한다.

| 참조 | 2 | 3 | 2 | 1 | 5 | 2 | 4 |
|---|---|---|---|---|---|---|---|
| 1 프레임 | 2 | 2 | 2 | 2 | 2 | 2 | 2 |
| 2 프레임 | - | 3 | 3 | 3 | 5 | 5 | 5 |
| 3 프레임 | - | - | - | 1 | 1 | 1 | 4 |
| Page Fault | V | V | - | V | V | - | V |

5번째 참조(5)에서는 가장 오래 쓰이지 않은 3이 나가고, 7번째 참조(4)에서는 1이 나간다. **답: 5**

**LFU ▲. 참조 횟수가 가장 적은 페이지를 내보낸다**

(단, 참조 횟수가 동일할 경우 FIFO 알고리즘으로 페이지를 교체한다.)

1. 참조 횟수를 적는다.
2. 페이지 자리는 그대로 두고 참조되면 횟수만 +1 한다.
3. Page Fault + 빈 프레임이 없음 → 참조 횟수가 적은 페이지를 교체한다.
4. 참조 횟수가 같을 때만 **FIFO**로 먼저 들어온 페이지를 찾는다.
5. 이전 메모리에 참조하는 페이지가 있었는지 확인하면서 Page Fault를 체크한다.

| 참조 | 2 | 3 | 2 | 1 | 5 | 2 | 4 |
|---|---|---|---|---|---|---|---|
| 1 프레임 | 2(1) | 2(1) | 2(2) | 2(2) | 2(2) | 2(3) | 2(3) |
| 2 프레임 | - | 3(1) | 3(1) | 3(1) | 5(1) | 5(1) | 5(1) |
| 3 프레임 | - | - | - | 1(1) | 1(1) | 1(1) | 4(1) |
| Page Fault | V | V | - | V | V | - | V |

5번째 참조에서 3과 1의 횟수가 같다(1). 3이 먼저 들어왔으므로 3이 나간다. 7번째 참조에서는 1과 5의 횟수가 같고, 1이 먼저 들어왔으므로 1이 나간다. **답: 5**

### 2) 프로세스 ◇

**(1) 프로세스 상태 †**

| 상태 | 설명 |
|---|---|
| 생성(New) | 프로세스가 만들어지는 중 |
| 준비(Ready) | CPU 할당을 기다리는 중 |
| 실행(Running) | CPU를 할당받아 실행 중 |
| 대기(Waiting) | 입출력 등 이벤트 완료를 기다리는 중 |
| 종료(Terminated) | 실행이 끝남 |

**(2) 교착 상태(Deadlock) †**

| 구분 | 키워드 |
|---|---|
| 발생 조건 4가지 ▲ | 상호 배제, 점유와 대기, 비선점, 환형 대기 (4개가 모두 성립해야 발생) |
| 해결 방법 | 예방(조건 하나를 깨뜨림), 회피(은행가 알고리즘), 탐지, 회복 |

**(3) 프로세스 스케줄링 ◆**

| 비선점형 스케줄링 | | 선점형 스케줄링 | |
|---|---|---|---|
| 종류 | 설명 | 종류 | 설명 |
| **FIFO** | 도착 순서대로 할당 | **Round Robin** ▲ (RR, 라운드 로빈) | FIFO + 시간 지정 (같은 시간 할당) |
| **HRN** | SJF + 대기 시간 고려 | **SRT** ▲ | 선점형 SJF |
| 기한부 | 마감시간 임박한 프로세스 먼저 | | |
| 우선순위 | 우선순위에 따라 할당 | | |

SJF ▲는 실행 시간이 짧은 프로세스에 먼저 할당하는 방식이며, **비선점형/선점형 둘 다 가능**하다. 선점형 SJF가 곧 SRT다.

HRN † 우선순위는 `(대기 시간 + 서비스 시간) / 서비스 시간`이고 값이 클수록 먼저 할당한다. 오래 기다린 긴 작업도 결국 차례가 오게 만드는 장치다.

라운드 로빈은 마트 계산대에서 한 사람이 3분씩만 계산하고 다시 줄 맨 뒤로 가는 방식에 빗댈 수 있다. 시간 할당량(Time Quantum) 안에 끝나지 않으면 줄 뒤로 돌아간다.

계산 공식은 세 가지만 기억하면 된다.

- 반환 시간 = 종료 시간 − 도착 시간 (= 대기 시간 + 실행 시간)
- 대기 시간 = 반환 시간 − 실행 시간
- 평균은 프로세스 개수로 나눈다.

**문제 1. SRT.** 아래 프로세스가 준비 큐에 도착했을 때 평균 대기 시간과 평균 반환 시간은?

| 프로세스 | 도착 시간 | 실행 시간 |
|---|---|---|
| P1 | 0 | 3 |
| P2 | 1 | 1 |
| P3 | 2 | 4 |
| P4 | 3 | 2 |

실행 순서: `P1(0~1) → P2(1~2) → P1(2~4) → P4(4~6) → P3(6~10)`

| 프로세스 | 종료 | 반환 | 대기 |
|---|---|---|---|
| P1 | 4 | 4 | 1 |
| P2 | 2 | 1 | 0 |
| P3 | 10 | 8 | 4 |
| P4 | 6 | 3 | 1 |

- 평균 대기 시간 : (1 + 0 + 4 + 1) / 4 = **1.5**
- 평균 반환 시간 : (4 + 1 + 8 + 3) / 4 = **4**

**문제 2. RR (시간 할당량 = 3).** 프로세스 조건은 문제 1과 같다.

실행 순서: `P1(0~3) → P2(3~4) → P3(4~7) → P4(7~9) → P3(9~10)`

| 프로세스 | 종료 | 반환 | 대기 |
|---|---|---|---|
| P1 | 3 | 3 | 0 |
| P2 | 4 | 3 | 2 |
| P3 | 10 | 8 | 4 |
| P4 | 9 | 6 | 4 |

- 평균 대기 시간 : (0 + 2 + 4 + 4) / 4 = **2.5**
- 평균 반환 시간 : (3 + 3 + 8 + 6) / 4 = **5**

**문제 3. 어려운 RR (시간 할당량 = 2).** 도착 시간이 달라진 경우다.

| 프로세스 | 도착 시간 | 실행 시간 |
|---|---|---|
| P1 | 0 | 3 |
| P2 | 1 | 1 |
| P3 | 2 | 4 |
| P4 | 4 | 2 |

실행 순서: `P1(0~2) → P2(2~3) → P3(3~5) → P1(5~6) → P4(6~8) → P3(8~10)`

대기실(큐)의 변화를 보면 이해가 쉽다. 시간 5에서 P3의 할당 시간이 끝날 때, P4는 시간 4에 이미 도착해 있다. 그래서 큐는 `P1, P4, P3` 순서가 된다. **새로 도착한 프로세스가 선점된 프로세스보다 먼저 줄을 선다**는 규칙을 적용한 것이다.

| 프로세스 | 종료 | 반환 | 대기 |
|---|---|---|---|
| P1 | 6 | 6 | 3 |
| P2 | 3 | 2 | 1 |
| P3 | 10 | 8 | 4 |
| P4 | 8 | 4 | 2 |

- 평균 대기 시간 : (3 + 1 + 4 + 2) / 4 = **2.5**
- 평균 반환 시간 : (6 + 2 + 8 + 4) / 4 = **5**

RR 문제는 도착과 동시에 끝나는 경우의 큐 삽입 순서를 먼저 정하고 푸는 것이 좋다. 문제에서 별도 규칙을 주지 않으면 "새 도착이 먼저"가 일반적이다.

### 4) OSI 7계층 † ◇

> **PDU**(Protocol Data Unit) = 각 계층에서 데이터를 부르는 단위다.

| 계층 | PDU | 주요 프로토콜/장비 | 키워드 |
|---|---|---|---|
| 7 응용 | 데이터 | HTTP, FTP, SMTP, DNS | 사용자 인터페이스, 응용 서비스 |
| 6 표현 | 데이터 | SSL/TLS, JPEG | 암호화, 압축, 코드 변환 |
| 5 세션 | 데이터 | RPC, NetBIOS | 연결 설정·유지·종료, 동기화 |
| 4 전송 | 세그먼트 | TCP, UDP | 종단 간 통신, 흐름 제어, 포트 번호 |
| 3 네트워크 | 패킷 | IP, ICMP, 라우터 | 경로 설정(라우팅), 논리 주소 |
| 2 데이터 링크 | 프레임 | 이더넷, HDLC, 스위치/브리지 | 물리 주소(MAC), 오류 제어 |
| 1 물리 | 비트 | 리피터, 허브, 케이블 | 전기적 신호 전송 |

전송 계층의 두 프로토콜은 성격이 정반대다.

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 (3-way handshake) | 비연결 |
| 신뢰성 | 재전송, 순서 보장 | 보장하지 않음 |
| 속도 | 상대적으로 느림 | 빠름 |
| 용도 | 웹, 메일, 파일 전송 | 스트리밍, DNS, 실시간 통화 |

TCP 연결은 `SYN → SYN+ACK → ACK` 세 번의 교환으로 맺는다.

※ AS : 자율시스템(하나의 관리 주체가 운영하는 네트워크 영역)

### 10) 서브넷 마스크 ◇

IP 주소는 아파트 주소에 빗댈 수 있다. 앞부분이 동(네트워크), 뒷부분이 호수(호스트)다. 그 경계를 알려 주는 별도의 32비트 값이 서브넷 마스크다.

**(1) IP 주소와 마스크의 관계**

주소 `192.168.1.200/26`, 마스크 `255.255.255.192`일 때 마지막 옥텟만 보면 아래와 같다.

| 구분 | 앞 3개 옥텟 | 마지막 옥텟 |
|---|---|---|
| | 네트워크 부분(프리픽스) · 26비트 | 호스트 부분 6비트 |
| IP 주소 | 11000000.10101000.00000001 | **11** 001000 |
| 마스크 | 11111111.11111111.11111111 | **11** 000000 |

- 마스크의 **1** : 네트워크 위치 / 마스크의 **0** : 호스트 위치
- 마스크는 IP 주소에 덧붙는 부분이 아니다. 경계를 알려 주는 별도의 32비트 값이다. 연속된 1은 네트워크 부분에, 뒤의 0은 호스트 부분에 대응한다.

**(2) IP 주소 구하는 방법 ▲**

| 주소 | 구하는 방법 |
|---|---|
| **네트워크 주소** ▲ | IP 주소 **AND** 서브넷 마스크 |
| **할당 가능한 호스트 주소** | 전체 IP 주소 중 네트워크 주소와 브로드캐스트 주소 **제외** |
| **브로드캐스트 주소** ▲ | 네트워크 주소 **OR** (NOT 서브넷 마스크) |

위 예제를 계산하면 다음과 같다. †

| 항목 | 계산 | 결과 |
|---|---|---|
| 네트워크 주소 | 200 AND 192 = 11001000 AND 11000000 | 192.168.1.**192** |
| 브로드캐스트 주소 | 192 OR 63 = 11000000 OR 00111111 | 192.168.1.**255** |
| 할당 가능 호스트 | 192.168.1.193 ~ 192.168.1.254 | 2⁶ − 2 = **62개** |

### 11) 서브넷팅 ◇

**(1) 기본 공식**

- IPv4 주소 32비트 = **네트워크 부분(프리픽스)** + **호스트 부분**
- `/n`의 n = 프리픽스 길이 = 마스크에서 연속된 1의 수
- 호스트 비트 수 h = 32 − n / 전체 주소 수 = 2<sup>h</sup>

**(2) 주소 범위에서 프리픽스 역산 ▲**

한 서브넷의 범위가 `10.0.0.0 ~ 10.0.0.15`일 때를 보자.

1. 전체 주소 수 = 15 − 0 + 1 = 16 = 2⁴
2. 호스트 비트 = 4
3. 프리픽스 = 32 − 4 = 28 → **/28**

원래 `/27`을 2등분했다면 `/27`은 원래 망이고, `/28`은 나눈 서브넷의 길이다.

**(3) FLSM. 호스트 앞 비트를 빌려 분할**

- 뒤쪽 비트를 고정(`XXXXXX00`)하면 0, 4, 8, …처럼 흩어져 **연속된 CIDR 범위가 되지 않는다.** 그래서 반드시 앞쪽 비트를 빌린다.

**(4) /24에서 빌린 비트 수에 따른 변화 ▲**

| 빌린 비트 수 | 서브넷 수 | 서브넷당 주소 수 | 프리픽스 | 마스크 끝자리 |
|---|---|---|---|---|
| 1비트 | 2 | 128 | /25 | 128 |
| 2비트 | 4 | 64 | /26 | 192 |
| 3비트 | 8 | 32 | /27 | 224 |
| 4비트 | 16 | 16 | /28 | 240 |

- 서브넷당 주소 수 + 마스크 끝자리 = 256이다. (128+128, 64+192, 32+224, 16+240)
- 각 서브넷의 호스트 비트 수 = 8 − 빌린 비트 수

**(5) 192.168.1.0/24를 /26 네 개로 분할**

| 마지막 자리 8비트 | 주소 범위 (마지막 자리) |
|---|---|
| 00XXXXXX | 0 ~ 63 |
| 01XXXXXX | 64 ~ 127 |
| 10XXXXXX | 128 ~ 191 |
| 11XXXXXX | 192 ~ 255 |

X는 남은 호스트 비트이고, 서브넷 비트 조합은 00 · 01 · 10 · 11이다. 공통 앞부분은 `192.168.1.`이며, 각 서브넷의 처음은 네트워크 주소, 끝은 브로드캐스트 주소다.

**(6) 필요한 서브넷 수로 FLSM 계산 ▲**

**문제.** `234.122.1.0/24`를 FLSM으로 3개 서브넷으로 분할하면 2번 서브넷의 브로드캐스트 주소는?

1. **서브넷 3개 필요** → 2ⁿ ≥ 3을 만족하는 최소 n = **2**. 호스트에서 2비트를 빌린다. (/24 → /26)
2. 마지막 자리 8비트를 **서브넷 앞 2비트 + 호스트 뒤 6비트**로 나눈다. `11101010.01111010.00000001.` `[00` `XXXXXX]`
3. 앞 2비트를 00 · 01 · 10으로 바꿔 서브넷을 만든다. (각 /26, 2⁶ = 64개)

| 서브넷 비트 | 서브넷 | 네트워크 주소 |
|---|---|---|
| 00 | 1번 서브넷 | 234.122.1.0 |
| 01 | 2번 서브넷 | 234.122.1.64 |
| 10 | 3번 서브넷 | 234.122.1.128 |
| 11 | (여분 · 미사용) | 234.122.1.192 |

4. 2번 서브넷(01)의 **브로드캐스트** = 호스트 6비트를 모두 1로 → `11101010.01111010.00000001.01111111` → **234.122.1.127**

| `mkdir` † | 디렉터리 생성 | `cp` / `mv` † | 복사 / 이동·이름 변경 |
| `rm` † | 파일 삭제 | `ps` / `kill` † | 프로세스 확인 / 종료 |
| `chmod` | 권한 변경 | `chown` † | 소유자 변경 |

**(2) 8진수 권한 설정 ▲**

`chmod [사용자권한][그룹권한][기타권한] file.txt` 형태이며, 예를 들면 `chmod 754 file.txt`다.

| 자리 | 사용자 | 그룹 | 기타 |
|---|---|---|---|
| 숫자 | 7 | 5 | 4 |
| 계산 | 읽기 + 쓰기 + 실행 = 4+2+1 | 읽기 + 실행 = 4+1 | 읽기 = 4 |
| 표기 † | rwx | r-x | r-- |

**(3) 스크립트 읽기 연습 †**

```sh
#!/bin/bash
sum=0
for i in 1 2 3 4 5
do
  sum=$((sum + i))
done
echo "합계: $sum"
```

출력은 `합계: 15`다. 변수는 `$`로 꺼내 쓰고, 산술은 `$(( ))` 안에서 계산한다.

|---|---|---|

| **MC/DC** | Modified Condition/Decision | **개별 조건식**이 결과에 **독립적으로 영향** |

※ 엄밀히는 결정 커버리지와 조건 커버리지가 서로를 포함하지 않는다. 시험에서는 위 순서로 외운다.

`if (A && B)` 하나를 예로 들면 차이가 선명해진다. †

| 커버리지 | 테스트 케이스 (A, B) | 개수 | 포인트 |
|---|---|---|---|
| 구문 | (T, T) | 1 | 문장이 한 번 실행되면 충족 |
| 결정 | (T, T), (F, T) | 2 | 결정문 결과가 참과 거짓을 각각 한 번 |
| 조건 | (T, F), (F, T) | 2 | 각 조건이 참/거짓을 모두 가짐. 결과는 둘 다 거짓이라 결정 커버리지는 미충족 |
| 조건/결정 | (T, T), (F, F) | 2 | 조건과 결정을 동시에 충족 |
| MC/DC | (T, T), (T, F), (F, T) | 3 | 한 조건만 바꿨을 때 결과가 바뀌는 쌍이 각 조건마다 존재 (n+1개) |

### 2) 블랙박스 테스트 ◆

내부 코드는 보지 않고 입력과 출력만 본다. 유형이 많아서 "무엇을 기준으로 케이스를 만드는가"로 구분하면 정리가 쉽다.

| 블랙박스 테스트 유형 | 영어 | 핵심 키워드 |
|---|---|---|
| **동등 분할** ▲ | Equivalence Partitioning | 입력 데이터를 **유효/무효** 그룹화 |
| **경계값 분석** ▲ | Boundary Value Analysis | 등가 분할 후 **경계값** 포함해 테스트 설계 |
| **결정 테이블** | Decision Table | **논리적 조건**과 그에 따른 **행동**을 표로 정리 |
| **원인-결과 그래프** ▲ | Cause-Effect Graph | **입력(원인)**이 **출력(결과)**에 미치는 영향을 그래프로 표현, 테스트 케이스 선정 |
| **상태 전이** | State Transition | **상태 변화** 기반 테스트 설계 |
| **오류 예측** | Error Guessing | 테스터의 **경험과 직관**, 오류 발생 부분 예측 |
| **비교 테스트** | Comparison Testing | 여러 버전 또는 제품을 **비교** 테스트 |
| **페어와이즈 테스트** | Pairwise Testing | 모든 입력 조합 대신 값들의 모든 **쌍(pair)**을 테스트하는 최소 케이스 |
| **분류 트리 테스트** | Classification Tree | 테스트 관련 요소를 **트리 구조**로 분석해 케이스 도출 |
| **유스케이스 테스트** | Use Case Testing | 사용자 **시나리오**(유스케이스) 기반 테스트 |

### 2) 응집도 · 결합도 † ★

좋은 모듈은 안은 단단하고, 밖과는 느슨하다. 즉, **응집도는 높게, 결합도는 낮게** 만든다.

**응집도** : 강한(좋음) → 약한(나쁨). 암기 **기순교절시논우**

| 응집도 | 키워드 |
|---|---|
| 기능적 | 모듈 내 모든 요소가 **하나의 기능** 수행 |
| 순차적 | 한 요소의 **출력**이 다음 요소의 **입력** |
| 교환적(통신적) | 같은 입력/출력 **데이터**를 사용 |
| 절차적 | **순서대로** 수행해야 하는 요소들 |
| 시간적 | **같은 시간대**에 실행되는 요소들 (예: 초기화) |
| 논리적 | 유사 성격 요소를 모아 두고 **매개**로 선택 |
| 우연적 | **관련 없는** 요소들이 모임 |

**결합도** : 약한(좋음) → 강한(나쁨). 암기 **자스제외공내**

| 결합도 | 키워드 |
|---|---|

| 제어 | **제어 신호**(플래그)로 흐름을 통제 |

| 내용 | **다른 모듈 내부**를 직접 참조 |

## 4-B. Java 객체지향 핵심

코드 문제는 개념만 알면 풀린다. 다형성이 나오면 두 가지만 확인하면 된다. 변수의 **선언 타입**이 무엇이고, 실제로 **new로 만든 객체**가 무엇인가.

<br>

### 1) 클래스와 객체 †

| 용어 | 의미 |
|---|---|
| 클래스 | 설계도 |
| 객체(인스턴스) | 설계도로 만든 실물. `new`로 생성 |
| 필드 / 메서드 | 객체가 가진 데이터 / 객체가 하는 일 |

```java
class Gamja {
  String name = "감자";          // 필드
  void print() {                 // 메서드
    System.out.println("우리는 " + name);
  }
}
class Main {
  public static void main(String[] args) {
    Gamja g = new Gamja();       // 객체 생성
    g.print();                   // 우리는 감자
  }
}
```

<br>

### 2) 상속 †

`extends`로 부모의 필드·메서드를 물려받는다. 자바는 클래스 **단일 상속**만 허용한다. 자식에서 부모를 가리킬 때는 `super`를 쓴다.

<br>

### 3) 추상 클래스 †

| 구분 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 키워드 | `abstract` / `extends` | `interface` / `implements` |
| 상속 | 단일 | 여러 개 구현 가능 |
| 멤버 | 일반 필드와 구현된 메서드를 가질 수 있음 | 상수와 메서드 선언 중심 |
| 객체 생성 | 불가 | 불가 |

<br>

### 4) 인터페이스 ◇ 쌩기초

클래스가 반드시 구현해야 할 메서드 목록을 먼저 정의한다. 콘센트 규격에 빗댈 수 있다. 규격(메서드 선언)만 정해 두고, 실제 전기 흐름(구현)은 기기(클래스)가 책임진다.

- 인터페이스에는 **메서드 선언만** 존재한다. (클래스와의 차이)
- 클래스가 그 메서드를 **구현**한다(`implements`).

```java
interface Edible {
  void eat(String who);                  // 메서드 선언
}
class Gamja implements Edible {          // 인터페이스 구현 약속
  @Override
  public void eat(String who) {          // 메서드 구현
    System.out.println(who + "가 감자를 먹음");
  }
}
class Main {
  public static void main(String[] args) {
    Gamja e1 = new Gamja();
    e1.eat("철수");                       // 구현된 메서드 호출 → 철수가 감자를 먹음
  }
}
```

단, **상수 필드**는 가능하다. 인터페이스 필드는 자동으로 `public static final`이다. 어디서나(public) 접근하고, 클래스에 하나(static)만 있으며, 값이 고정(final)된다. 즉, 곧 상수다.

<br>

### 6) 다형성과 부모-자식 대결 ★

다형성은 여러 가지 형태를 가질 수 있다는 뜻이다. 무엇이? 객체와 메서드가 그렇다.

**① 선언 타입은 부모, 실제 객체는 자식**

```java
Gamja g = new AlGamja();
```

선언 타입은 부모(`Gamja`), 실제 객체는 자식(`AlGamja`)이다. 이게 다형성이다. 문제는 이때 선언 타입편과 실제 객체편 중 **무엇을 보느냐**다.

| 구분 | 결정 기준 | 왜? · 시점 |
|---|---|---|
| **오버라이딩 실행** ▲ | **실제 객체편** · 런타임 | 자식이 재정의하면 자식 메서드가 실행된다 |
| **오버로딩 선택** ▲ | 선언 타입편 · 컴파일타임 | 선언 타입 시야에서 후보를 결정한다 |
| **static 메서드** ▲ | 선언 타입편 · 컴파일타임 | 타입(설계도)에 고정되어 객체를 안 본다 |
| **필드** ▲ | 선언 타입편 · 컴파일타임 | 오버라이딩 개념이 없고 선언 타입을 따른다 |
| **static 필드** ▲ | 선언 타입편 · 컴파일타임 | static 메서드와 동일 |

> **오버라이딩 실행만 실제 객체편이다. 오버로딩 · static · 필드는 선언 타입편이다.**

<br>

### 7) 오버라이딩 ▲ : 같은 메서드, 실제 객체 편

**Override = 덮어쓰기.** 자식이 부모의 말(메서드)에 올라타서 실행권을 가져간다. 이름·매개변수가 같은 `print()`를 자식이 다시 작성한다.

```java
class Gamja {                                   // 부모 클래스
  String name = "감자";
  void print() { System.out.println("우리는 " + name); }
}
class AlGamja extends Gamja {                   // 자식 클래스
  String name = "알감자";
  @Override                                     // 같은 메서드 재정의
  void print() { System.out.println("우리는 " + name); }
}
```

전체 프로그램의 스코프를 나누어 보면 이렇다.

| 영역 | 내용 |
|---|---|
| 클래스/설계도 | `Gamja` { name : String = "감자", print() } |
| 실제 객체 | `AlGamja` { name = "알감자", print() } ← 변수 `g`가 가리킴 |

실전 적용 코드는 다음과 같다.

```java
Gamja g = new AlGamja();
g.print();                      // 우리는 알감자   (오버라이딩 → 실제 객체 AlGamja의 print)
System.out.println(g.name);     // 감자           (필드 → 선언 타입 Gamja 기준)
```

타입은 `Gamja`, 객체는 `AlGamja`이므로 `print()`는 **자식 것**이 실행된다. 반면 `g.name`은 필드라서 선언 타입(`Gamja`)을 따라 `"감자"`가 나오는 함정이 자주 출제된다.

<br>

### 8) 오버로딩 ▲ (over-loading) : 같은 이름, 다른 매개변수

**Overload = 더 싣기.** 같은 `eat` 이름 위에 매개변수를 더 싣거나 자료형을 바꿔 여러 방식으로 쓴다. 메서드가 다양한 형태(다형성)를 가지게 된다.

```java
class Gamja {
  String name = "감자";
  void eat(String who) {                        // 매개변수 1개
    System.out.println(who + "가 먹음");
  }
  void eat(String who, int count) {             // 매개변수 2개 = 오버로딩
    System.out.println(who + "가 " + count + "개 먹음");
  }
}
```

```java
Gamja g = new Gamja();
g.eat("철수");        // 철수가 먹음
g.eat("철수", 3);     // 철수가 3개 먹음
```

| 구분 | 오버로딩 | 오버라이딩 |
|---|---|---|
| 한 줄 요약 | 이름은 같고 **매개변수가 다르다** | 이름·매개변수가 같고 **내용을 다시 쓴다** |
| 관계 | 같은 클래스(상속 관계에서도 가능) | 부모-자식 |
| 결정 시점 | 컴파일타임 | 런타임 |
| 결정 기준 | 선언 타입 | 실제 객체 |

반환 타입만 다른 경우는 오버로딩이 아니며 컴파일 오류가 난다. †

### 1) 서비스 거부 공격 † ◆

서비스 거부 공격은 서버가 감당할 수 없을 만큼 일을 시켜 정상 사용자를 밀어내는 공격이다. 식당에 예약 전화를 수백 통 걸어 진짜 손님이 못 들어오게 만드는 것에 빗댈 수 있다.

| 공격 | 핵심 키워드 |
|---|---|
| **Ping of Death** ▲ | ICMP 패킷을 **최대 크기 이상**으로 분할 전송, 재조합 시 시스템 장애 |
| **Smurf** ▲ | ICMP Echo Request를 **브로드캐스트**로 보내고 출발지를 **피해자 IP로 위조** → 응답 폭주 |
| **SYN Flooding** ▲ | TCP 3-way handshake에서 **SYN만** 보내 반개방(Half-Open) 연결 큐를 가득 채움 |
| **Teardrop** ▲ | IP 단편화 **offset 값을 조작**해 재조합 오류 유발 |
| **Land Attack** ▲ | **출발지와 목적지의 IP·포트를 같게** 위조 |
| **UDP Flooding** | 대량의 UDP 패킷 전송 |
| **HTTP GET Flooding** | 웹 서버에 정상처럼 보이는 GET 요청을 반복 |

| 분산 공격 | 핵심 키워드 |
|---|---|
| **DDoS** ▲ | 다수의 **좀비 PC(봇넷)**가 동시에 공격 |
| **DRDoS** ▲ | 출발지를 **피해자 IP로 위조**해 **반사 서버**에 요청 → 반사 서버가 피해자에게 응답을 보내 **증폭** |

### 3) 악성 코드 · 사회공학 공격 † ◆

기술이 아니라 사람을 속이는 공격이다. 아무리 단단한 자물쇠도 문을 열어 주는 사람이 있으면 소용이 없다.

| 공격 | 핵심 키워드 |
|---|---|
| **피싱** ▲ | 이메일 등으로 가짜 사이트에 유도해 정보 탈취 |
| **스미싱** ▲ | **문자(SMS)** 링크로 악성 앱 설치 유도 |
| **파밍** ▲ | DNS나 hosts 파일을 조작해 **정상 주소를 입력해도** 가짜 사이트로 이동 |
| **큐싱** | **QR 코드**를 이용한 피싱 |
| **스피어 피싱** | **특정 대상**을 노린 맞춤형 피싱 |
| **쇼울더 서핑** | 어깨너머로 입력 정보를 훔쳐봄 |
| **스캐빈징** | 쓰레기통 등에서 버려진 정보를 수집 |

### 4) 웹 애플리케이션 공격 · SW 보안 취약점 † ◆

| 공격 | 핵심 키워드 | 대응 |
|---|---|---|
| **SQL 삽입** ▲ | 입력값에 SQL을 끼워 넣어 DB 조작 | PreparedStatement(바인딩), 입력 검증, 최소 권한 |
| **XSS** ▲ | 게시글 등에 **스크립트를 삽입**해 다른 사용자 브라우저에서 실행 | 출력 시 이스케이프, 입력 검증 |
| **CSRF** ▲ | 사용자가 **로그인한 세션을 이용**해 의도하지 않은 요청을 보내게 함 | CSRF 토큰, Referer 검증 |
| 디렉터리 트래버설 | `../` 등으로 허용되지 않은 경로 접근 | 경로 검증 |
| 파일 업로드 취약점 | 악성 스크립트 파일을 업로드해 실행 | 확장자·형식 검증, 실행 권한 제거 |

XSS와 CSRF는 방향이 반대다. XSS는 사용자가 사이트를 믿는 점을, CSRF는 사이트가 사용자의 브라우저를 믿는 점을 노린다.

### 5) 암호 알고리즘 ◇

**(1) 대칭키 + 블록 암호 알고리즘**

> ▲ **대칭키** : 암호화키 = 복호화키. 비밀키 전달이 필요하다. 암호화/복호화가 **빠르다**.
> **블록 암호화** : 고정된 크기의 블록으로 나누어 암호화한다. 아래 알고리즘은 모두 블록 암호 알고리즘이다.

| 알고리즘 | 키워드 |
|---|---|
| **DES** ▲ | **IBM** 개발, **블록 64비트** (키 56비트 †) |
| **AES** ▲ | DES 성능 문제 극복, **블록 128비트** |
| **SEED** ▲ | **KISA** 개발, **한국 최초 표준** |
| **IDEA** ▲ | 초기 블록 암호 알고리즘 |
| **Skipjack** | 전화기와 같이 **음성 암호화**에 주로 사용 |

**(2) 비대칭키(공개키) 암호 알고리즘**

> ▲ **비대칭키** : **공개키/개인키**가 존재한다.

| 알고리즘 | 키워드 |
|---|---|
| **디피-헬만** | **최초**의 공개키 알고리즘, **이산 로그** 기반 |
| **RSA** | **소인수분해** 기반 |
| **ECC** | RSA 대안, **타원곡선 이산 로그** 기반, **짧은 키** |

**(3) 해시 암호 알고리즘**

> ▲ **해시 함수** : 임의의 길이를 갖는 데이터를 **고정된 길이**로 바꾸는 **단방향** 함수

| 알고리즘 | 키워드 |
|---|---|
| **MD5** | **무결성 검사**에 사용, R.Rivest 개발 (128비트 †) |
| **SHA-1** | **160비트**, NSA(1995) |
| **SHA-2**(256/384/512) | **256/384/512비트**, AES 대응, NSA(2001) |

### 13) 정보보호 관리체계 · 보안 솔루션 † ◆

정보보호의 3대 목표는 기밀성(허가된 사람만 본다), 무결성(허가 없이 바뀌지 않는다), 가용성(필요할 때 쓸 수 있다)이다.

| 구분 | 키워드 |
|---|---|
| **ISMS** | 정보보호 관리체계 인증 |

| **방화벽** ▲ | 내부와 외부 네트워크 사이에서 **허용/차단 규칙**으로 트래픽 통제 |
| **IDS** ▲ | 침입을 **탐지**만 한다 |
| **IPS** ▲ | 침입을 탐지하고 **차단**까지 한다 |
| **VPN** | 공중망 위에 **암호화된 가상 사설망** 구성 |
| **WAF** | **웹 애플리케이션** 공격(SQL 삽입, XSS 등) 방어 |
| **NAC** | 단말의 네트워크 접속을 **인증·통제** |
| **DLP** | 내부 **정보 유출 방지** |
| **허니팟** | 공격자를 유인하는 **미끼 시스템** |

정리해 보면 이 요약의 뼈대는 두 가지다. 하나는 ★ 항목을 소리 내어 설명할 수 있을 때까지 반복하는 것이다. 다른 하나는 ◆와 ◇ 항목을 기출에서 틀린 문제와 연결해 두는 것이다.

물론 모든 표를 처음부터 끝까지 외우는 방식도 가능하다. 하지만 시간이 한정되어 있다면 계산 문제를 먼저 손으로 풀어 보는 편이 점수에 직결된다. 페이지 교체, 스케줄링, 서브넷팅, 커버리지 문제는 한 번 풀어 본 사람과 아닌 사람의 차이가 크다.

시험 전날에는 새로운 범위를 늘리기보다 † 표시 항목과 계산 예제를 한 번 더 훑고, 보충한 부분은 교재나 기출로 대조해서 확인하는 것이 좋다.
