# 소프트웨어 설계 원리와 아키텍처 패턴


집을 지을 때 벽돌부터 쌓는 사람은 없다. 설계도부터 그린다. 소프트웨어도 같다. 이번 글은 설계도의 뼈대인 아키텍처와, 이미 검증된 설계 방식인 아키텍처 패턴을 다룬다.

<br>

### 소프트웨어 아키텍처란

소프트웨어를 구성하는 요소들과 그 사이의 관계를 표현하는 시스템의 구조다. 애플리케이션을 어떻게 나눌지, 나눠진 모듈에 어떤 기능을 맡길지, 모듈 간 인터페이스를 어떻게 둘지를 결정한다.

<br>

### 설계 4대 원리

| 원리 | 핵심 |
|---|---|
| 모듈화 | 시스템의 기능을 모듈 단위로 나눈다. 성능 향상, 수정과 재사용, 유지 관리가 쉬워진다 |
| 추상화 | 전체적이고 포괄적인 개념을 먼저 설계하고 차례로 세분화한다 |
| 단계적 분해 | 상위 개념에서 하위 개념으로 구체화한다. Niklaus Wirth가 제안한 하향식 전략이다 |
| 정보 은닉 | 모듈 내부의 절차와 자료를 감춰 다른 모듈이 접근하거나 바꾸지 못하게 한다 (캡슐화) |

모듈화에는 균형이 필요하다. 모듈을 너무 작게 나누면 개수가 늘어 통합 비용이 커진다. 너무 크게 나누면 모듈 하나의 개발 비용이 커진다.

추상화는 대상에 따라 세 가지로 나뉜다.

- 과정 추상화: 자세한 수행 과정은 감추고 전반적인 흐름만 보여 준다
- 데이터 추상화: 데이터의 세부 속성을 정의하지 않고 구조를 대표할 표현으로 대체한다
- 제어 추상화: 이벤트 발생의 정확한 절차를 정의하지 않고 대표 표현으로 대체한다

정보 은닉 덕분에 한 모듈이 바뀌어도 다른 모듈에 영향이 적다. 즉, 수정과 시험, 유지보수가 쉬워진다.

<br>

### 상위 설계와 하위 설계

| 구분 | 상위 설계 | 하위 설계 |
|---|---|---|
| 별칭 | 아키텍처 설계, 예비 설계 | 모듈 설계, 상세 설계 |
| 대상 | 시스템의 전체 구조 | 시스템의 내부 구조와 행위 |
| 세부 항목 | 구조, DB, 인터페이스 | 컴포넌트, 자료구조, 알고리즘 |

<br>

### 아키텍처 설계 과정

1. 설계 목표 설정: 요구사항을 분석해 전체 시스템의 설계 목표를 정한다
2. 시스템 타입 결정: 시스템과 서브시스템의 타입을 정하고 아키텍처 패턴을 선택한다
3. 아키텍처 패턴 적용: 시스템의 표준 아키텍처를 설계한다
4. 서브시스템 구체화: 서브시스템의 기능과 상호작용을 위한 동작, 인터페이스를 정의한다
5. 검토: 설계 목표와 요구사항, 설계 원리를 만족하는지 확인한다

컴포넌트 설계에는 협약에 의한 설계라는 개념이 쓰인다. 컴포넌트가 지켜야 할 약속을 인터페이스에 명세하는 방식이다.

| 조건 | 내용 |
|---|---|
| 선행 조건 | 오퍼레이션이 호출되기 전에 참이어야 할 조건 |
| 결과 조건 | 오퍼레이션이 수행된 후 만족되어야 할 조건 |
| 불변 조건 | 오퍼레이션이 실행되는 동안 항상 만족되어야 할 조건 |

<br>

### 아키텍처 패턴

아키텍처 패턴은 설계할 때 참조할 수 있는 전형적인 해결 방식이다. 서브시스템과 그 역할, 관계, 규칙이 정의되어 있다.

| 패턴 | 핵심 | 예시 |
|---|---|---|
| 레이어 | 시스템을 계층으로 구분한다. 서로 마주 보는 두 계층 사이에서만 상호작용한다 | OSI 참조 모델 |
| 클라이언트-서버 | 하나의 서버와 다수의 클라이언트로 구성한다 | 웹 서비스 |
| 파이프-필터 | 데이터 스트림 처리 단계를 필터로 캡슐화하고 파이프로 전달한다 | UNIX 쉘 |
| 모델-뷰-컨트롤러 | 서브시스템을 모델, 뷰, 컨트롤러로 나눈다 | 웹 프레임워크 |
| 마스터-슬레이브 | 마스터가 작업을 나눠 슬레이브에 맡기고 결과를 받는다 | 병렬 컴퓨팅, 장애 허용 시스템 |
| 브로커 | 브로커가 요청에 맞는 컴포넌트와 사용자를 연결한다 | 분산 환경 시스템 |
| 피어 투 피어 | 하나의 컴포넌트가 클라이언트도 서버도 될 수 있다 | 파일 공유 P2P |
| 이벤트 버스 | 소스가 채널에 이벤트를 발행하면 구독한 리스너가 받아 처리한다 | 알림 서비스 |
| 블랙보드 | 모든 컴포넌트가 공유 저장소에 접근한다 | 음성 인식, 신호 해석 |
| 인터프리터 | 코드 각 줄의 수행 방법을 지정하고 기호마다 클래스를 둔다 | 번역기, 컴파일러 |

모델-뷰-컨트롤러(MVC)는 가장 자주 만나는 패턴이다. 물론 한 파일에 화면과 로직을 다 넣는 편이 더 간단해 보인다. 하지만 화면이 늘어날수록 같은 로직을 여러 번 고치게 된다. MVC는 이 문제를 역할 분리로 푼다.

### 정리

패턴은 정답이 아니라 선택지다. 시스템의 성격을 먼저 파악하고 그에 맞는 패턴을 고르는 것이 좋다.
